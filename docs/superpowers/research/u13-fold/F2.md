# F2: Serve security majors

Each finding below is confirmed by an adversarial verifier (or by the conductor directly). Fold every one. Severity blocker findings are non-negotiable; majors may be adapted if the fix text conflicts with the code, but the defect must end up fixed.

## F2.1 [major] GET /api/journey/{id} mutates another user's session state and emails the admin before it checks ownership

File: /var/home/glw907/Projects/dubplate/internal/serve/api.go:85

`handleJourney` calls `j.advance(r.Context(), id, now)` at /var/home/glw907/Projects/dubplate/internal/serve/api.go:85, and only then builds the live set and calls `j.authorize(...)` at api.go:88-98. `advance` is not a read: it calls `journey.AdvanceInLibrary`, which appends a `ledger.StateInLibrary` event (internal/journey/journey.go:175-185), and then `journey.AdvanceStalled`, which appends a `ledger.StateStalled` event AND sends mail to the admin (journey.go:131-148).

Attack: Bob is on the roster (any family member). He learns or is shown Alice's 26-char session ID — from a shared screenshot, a copied URL, an admin mail subject that literally contains `Session %s ... contributor %s`, or an inbox directory name `<sessionid>__<album>`. Bob GETs `/upload/api/journey/<alice-id>`. He receives a 404 and learns nothing from the body, but the server has already:
  1. appended a `stalled` event to Alice's session if her latest event is older than `StallMinutes`, which is the de-dupe record, so it permanently suppresses the real stall notification that would have fired later; and
  2. sent the admin an email titled "dubplate: alice@…'s upload has stalled".
That is unauthenticated-relative-to-the-resource state mutation plus notification forgery, triggerable at 5-second poll cadence.

It also defeats the no-existence-oracle property the surrounding comments claim (api.go:69-71, api.go:218-221). `advance` returns instantly when `len(events) == 0` (api.go:190-194) but makes an outbound Navidrome `getScanStatus` HTTP call (10s-bounded) when the session exists and is in `tagging`. The response-time difference between "this session ID exists in the ledger" and "it does not" is trivially measurable, and it is exactly the distinction the 404 shape was designed to hide.

Proposed fix: Move the `advance` call below the authorization check: build `lb`, run `j.authorize(id, email, lb)`, 404 on failure, and only then `advance`. `authorize` already reads the ledger itself, so the reordering costs nothing.

## F2.2 [major] Unvalidated tus upload ID reaches filepath.Join; percent-encoded traversal confirmed working end to end

File: /var/home/glw907/Projects/dubplate/internal/serve/upload.go:326

`enforceUploadOwnership` derives the upload ID as `id := strings.Trim(r.URL.Path, "/")` (/var/home/glw907/Projects/dubplate/internal/serve/upload.go:326) and hands it straight to `e.store.GetUpload(r.Context(), id)` (upload.go:338). tusd's `filestore` performs no ID validation whatsoever: `infoPath` is `filepath.Join(store.Path, id+".info")` and `defaultBinPath` is `filepath.Join(store.Path, id)` (filestore.go:195-202). tusd's own handlers use the identical `strings.Trim(path, "/")` extraction (handler/unrouted_handler.go:1678-1680), so whatever ID gets past this middleware is the ID tusd's HEAD/PATCH/DELETE act on.

Go's ServeMux only canonicalizes the *escaped* path, so `..%2f` survives every layer: `mountBasePath` matches on `r.URL.Path`, `http.StripPrefix` trims both `Path` and `RawPath`, and the middleware then reads the decoded `r.URL.Path`. Verified live against the dev binary on 127.0.0.1:8090. I planted a syntactically valid tusd `.info` file one directory above UploadsDir with `MetaData.email` set to the dev identity, then:

    files/zzprobe            404
    files/%2e%2e/zzprobe     404   (encoded dots, path stays multi-segment)
    files/..%2fzzprobe       200   <-- traversal succeeded
    files/%2e%2e%2fzzprobe   200   <-- traversal succeeded

The 200s mean `filepath.Join(UploadsDir, "../zzprobe.info")` was read, the ownership check passed on its metadata, and tusd's HeadFile served it. Probe file removed afterwards.

Honest exploitability bound: to weaponize this an attacker needs a file at a traversable path that (a) ends in `.info`, (b) parses as tusd `handler.FileInfo` JSON, and (c) carries their own verified email in `MetaData`. They cannot plant one, because `preCreate` overrides `changes.ID` with the server-chosen `sess.ID + "-" + slot` (upload.go:430-437). So this is a latent traversal rather than a live read/write primitive today. It is still a real defect: the app validates session IDs with `validSessionID` at every other ingress (upload.go:383, upload.go:909, api.go:79, serve.go:535) and skips validation on the one path that feeds an unguarded `filepath.Join`, leaving the whole chain one tusd or config change away from arbitrary-path reads and DELETEs.

Proposed fix: In `enforceUploadOwnership`, validate the ID against the shape `preCreate` actually mints before touching the store: `^[a-z2-7]{26}-[0-9]+$`. Anything else gets `http.NotFound`, consistent with the existing no-oracle 404 shape. This is the same discipline `validSessionID` already applies everywhere else.

## F2.3 [major] Completed sessions are never removed from the store and never swept from disk: unbounded memory and disk growth

File: /var/home/glw907/Projects/dubplate/internal/serve/session.go:330

`Engine.completeSession` runs a session to a terminal outcome and returns, but never calls `e.sessions.delete(sess.ID)` (/var/home/glw907/Projects/dubplate/internal/serve/upload.go:625-663). The only deleter is `SweepOnce` (upload.go:768-776), which targets `e.sessions.expired(cutoff)` — and `expired` explicitly filters to `!done && sess.createdAt.Before(cutoff)` (internal/serve/session.go:330-334). A completed session is therefore permanently resident in the `Store` map, holding its `verdicts` slice.

Disk is worse. Trace each terminal branch:
  - format verdict fails -> `e.discard(sess)` removes the dir (upload.go:637). Memory leaks, disk is fine.
  - private lane / confident match -> `promote` renames the dir into the inbox. Memory leaks, disk is fine.
  - `PushedBack` (unconfident tag match) -> dir deliberately left under UploadsDir (upload.go:656-657).
  - `ProbeUnavailable` -> dir deliberately left under UploadsDir (upload.go:652-654).
  - `promoteInto` rename failure -> dir deliberately left in place (upload.go:672-677).
None of the last three is ever reclaimed by anything: not the sweep (session is `completed`), not a systemd timer (nothing in systemd/ or scripts/deploy.sh touches /srv/music/uploads), not a `dubplate` subcommand. Every pushed-back album accumulates full-size FLAC content forever.

The failure mode is a slow lockout: `preCreate` rejects with `ReasonNoSpace` once `avail - Size < FreeFloorGB` (upload.go:421-428). With the default 5 GiB floor and a family sending lossless albums, a handful of pushed-back uploads is enough. Combined with the TagProbe blocker above, *every* main-lane upload currently lands in this bucket.

Proposed fix: Two changes. (1) Give the sweep a second cutoff for settled sessions: sweep a completed session's store entry after a short grace (long enough for the journey poll to read the outcome back), so the map does not grow without bound. (2) Give `PushedBack` / `ProbeUnavailable` / failed-promote directories an explicit retention TTL and reclaim them on the same ticker, or move them to a reviewable holding directory an operator sees, rather than leaving them where the free-space admission check will eventually trip over them.

## F2.4 [major] The partial-upload sweep is memory-only, so any serve restart permanently orphans staged directories and breaks tus resume

File: /var/home/glw907/Projects/dubplate/internal/serve/upload.go:768

`SweepOnce` finds its targets by iterating the in-process `Store` map (/var/home/glw907/Projects/dubplate/internal/serve/upload.go:768-776 and internal/serve/session.go:324-337). It never scans UploadsDir. The `Store` is plain in-memory state with no persistence (session.go:244-252).

So on every `systemd restart dubplate-serve` — a deploy, a crash, `Restart=` firing — the entire session map is discarded while the on-disk artifacts survive: assembled session directories `<UploadsDir>/<sessionid>/`, raw tus blobs `<UploadsDir>/<sessionid>-<slot>`, and their `.info` sidecars. Nothing will ever delete them. `PartialTTL` (24h default) becomes decorative: it only ages out sessions the process still remembers.

The contributor-facing half is worse than the disk half. After a restart, a resuming tus client's PATCH passes `enforceUploadOwnership` (the `.info` file still carries their email), reaches `preFinish`, and hits `e.sessions.get(sessionID)` returning not-found -> `fmt.Errorf("serve: session %s vanished before finish", ...)` -> a 500 (upload.go:450-454). The whole point of tus here is resumable uploads over a family member's phone connection, and the web store surfaces `resumable` history rows; a routine deploy silently converts every in-flight resumable upload into a hard failure with an internal-sounding error.

Proposed fix: Make the sweep filesystem-driven rather than map-driven: at each tick (and once at startup), stat every entry under UploadsDir and remove anything older than `PartialTTL` that the live map does not claim. That reclaims restart orphans and is the only version of the sweep that is correct across a restart. For resume specifically, either persist minimal session metadata (the sidecar shape is already defined) or reconstruct the session from the surviving `.info` metadata in `preFinish` instead of 500-ing.

## F2.5 [major] expected_files is unbounded and no aggregate album cap is enforced, so the advertised max_album_bytes is not a real limit on the multi-file path

File: /var/home/glw907/Projects/dubplate/internal/serve/upload.go:888

`Store.create` validates only `expectedFiles < 1` (/var/home/glw907/Projects/dubplate/internal/serve/session.go:257-259); nothing upstream bounds it either, since `handleCreateSession` decodes the JSON and passes it through (internal/serve/upload.go:888). tusd's `MaxSize` is set to `cfg.Upload.MaxAlbumBytes` but bounds one tus resource, and the code comment concedes it is not an aggregate cap, deferring to "Decide's callers rejecting an oversized member" (upload.go:248-254). `intake.Decide` does no size arithmetic at all — it is a pure AND over per-file `OK` flags (internal/intake/intake.go:45-54). There is no aggregate check anywhere.

So a session declaring `expected_files: 500` admits 500 tus uploads of up to 2 GiB each. The only backstop is the per-create free-space floor (upload.go:421-428), which means the enforced ceiling is "fill the disk down to FreeFloorGB", not 2 GiB.

This is also a copy-contract break, not only a resource one. `GET /api/config` serves `max_album_bytes: 2147483648` and `format_spec: "FLAC only, 44100 Hz / 16-bit or better, one album per upload, up to 2.0 GiB total."` (verified live), and `SpecCard.svelte:44,70` renders "up to 2.0 GiB" to the contributor as an album total. `formatSpecText` is explicitly justified as rendering "the actual enforced constants ... never hand-written prose that could drift from what the gate enforces" (internal/serve/serve.go:409-414) — but for the multi-file path that sentence describes a limit the server does not enforce.

Secondary: `expected_files` also sizes `Session.reserve`'s slot budget, so a single request can pin a large number of pending upload slots and grow `sess.verdicts` unboundedly.

Proposed fix: Cap `expected_files` at a defensible per-album maximum (`intake`'s own `maxZipEntries = 2000` is the natural sibling constant, or something far tighter like a few hundred) and reject above it with a `reject.Reason`. Then track admitted bytes on the `Session` under its mutex and reject at `preCreate` when `admitted + hook.Upload.Size > MaxAlbumBytes`, so the multi-file path enforces the same total the ZIP path and the UI both promise.

## F2.6 [major] No CSRF defense on any state-changing POST: /api/session accepts a CORS-simple cross-origin request

File: /var/home/glw907/Projects/dubplate/internal/serve/upload.go:877

Nothing in `internal/serve/` inspects `Origin`, `Referer`, or `Sec-Fetch-Site`, and `handleCreateSession` decodes the body without checking `Content-Type` (/var/home/glw907/Projects/dubplate/internal/serve/upload.go:877-881). Verified live against the dev binary:

    curl -X POST -H 'Content-Type: text/plain' -H 'Origin: https://evil.example' \
         --data '{"album":"csrf test","collection":"","expected_files":1}' \
         http://127.0.0.1:8090/upload/api/session
    -> HTTP/1.1 201 Created  {"session_id":"srum5ssgaxtxkdz5xlmv5zbpim"}

`text/plain` + no custom headers is precisely the shape a cross-origin `<form>` or `fetch` can send with no preflight, so nothing in the browser stops it reaching the origin. `POST /api/stream/probe` has the same property.

Concrete impact if the request carries credentials: `MaxSessionsPerUser` is 3 and `PartialTTL` is 24h (internal/config/config.go:180-181). Three cross-site POSTs from a page a family member visits exhaust their entire session quota, and `countActive` counts non-completed sessions, so `preCreate` and `handleCreateSession` both start answering `ReasonTooManySessions` for a full day. The victim cannot upload and has no way to clear it.

Whether the browser attaches the credential is not this code's decision to leave to chance: the Access `CF_Authorization` cookie's `SameSite` attribute is a Zero Trust application setting, and cloudflared injects `Cf-Access-Jwt-Assertion` from whatever cookie arrives. The tus surface is incidentally protected (`Tus-Resumable`/`Upload-Length` force a preflight, and tusd's default CORS config is `AllowOrigin: .*` with `AllowCredentials: false`), but `/api/session` and `/api/stream/probe` are not.

Proposed fix: Add one middleware in front of the mux that rejects any non-GET/HEAD whose `Origin` (falling back to `Sec-Fetch-Site: same-origin`) does not match the configured public origin, and require `Content-Type: application/json` on the JSON POSTs. Do not rely on the Access cookie's SameSite value. See the OWASP CSRF Prevention Cheat Sheet's "Verifying Origin With Standard Headers" section; Cloudflare's Zero Trust docs cover the cookie settings that determine whether the credential rides along at all.

## F2.7 [major] No baseline security response headers on any response, including the app document

File: /var/home/glw907/Projects/dubplate/internal/serve/serve.go:201

`staticHandler` sets only `Cache-Control` (/var/home/glw907/Projects/dubplate/internal/serve/serve.go:201-211), `writeJSON` sets only `Content-Type` (upload.go:930-934), and nothing wraps the mux with a header middleware. A repo-wide grep for `Content-Security-Policy`, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, and `Strict-Transport-Security` across Go, HTML, TS, JSON, and YAML returns nothing outside tests. Confirmed against the live dev binary:

    HTTP/1.1 200 OK
    Accept-Ranges: bytes
    Cache-Control: no-cache
    Content-Length: 406
    Content-Type: text/html; charset=utf-8
    Date: ...

That is the whole response. Missing:
  - `X-Content-Type-Options: nosniff` — every asset `http.FileServerFS` returns is sniffable. (Note the contrast: Go's own `http.Error` sets nosniff, so the error paths are better protected than the app itself.)
  - `Content-Security-Policy` — no `default-src 'self'`, no `frame-ancestors 'none'`.
  - `X-Frame-Options` / `frame-ancestors` — the uploader can be framed by any site. A family member with a live Access session can be shown the real uploader in an invisible frame and clickjacked into actions on it.
  - `Referrer-Policy` — nothing constrains what leaves in `Referer`.
  - `Strict-Transport-Security` — may be supplied at the Cloudflare edge, but nothing in the repo records that, so it is unverifiable from here.

See the OWASP Secure Headers Project and the OWASP HTML5 Security Cheat Sheet.

Proposed fix: Add one `securityHeaders` middleware wrapping the whole handler in `NewServer`, alongside `mountBasePath`: `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, and a CSP of roughly `default-src 'self'; frame-ancestors 'none'; base-uri 'none'; object-src 'none'; form-action 'self'` (the app is a static Vite bundle with no third-party origins, so a tight policy costs nothing). Set HSTS at the edge and record that decision in the repo.

## F2.8 [major] POST /api/stream/probe is a gate-measurement endpoint shipped in the production route table with no cap and no deadline

File: /var/home/glw907/Projects/dubplate/internal/serve/serve.go:188

`handleStreamProbe` is registered unconditionally in `buildMux` (/var/home/glw907/Projects/dubplate/internal/serve/serve.go:188) and is described in its own doc comment as existing "solely to prove ... that cloudflared delivers bytes incrementally" for gate 1 (serve.go:428-439). STATUS records gates 1-2 as already PASSED, so this endpoint's purpose is served, yet it stays in the production surface.

As written it is a resource sink. It clears the write deadline (`rc.SetWriteDeadline(time.Time{})`, serve.go:458), then loops on a 15s ticker with no maximum duration, no concurrent-stream cap per identity, and no global cap (serve.go:478-490). The only exit is client disconnect or shutdown. Each open stream pins a goroutine, a connection, and a `*http.Server` conn slot indefinitely. Any single on-roster caller can open thousands with a trivial script and exhaust the process; because it is a CORS-simple POST with no body requirements (see the CSRF finding), a cross-site page can open them from a victim's browser too.

It also carries the unbounded `Last-Event-ID` -> `strconv.Atoi` reflection at serve.go:448-452, harmless on its own but more attack surface than a retired probe should have.

Proposed fix: Delete the route now that gate 1 has passed; the handler can stay in the tree behind a build tag or a config flag if it is wanted for a future re-measurement. If it must ship, bound it: a hard max stream duration, a per-identity concurrent-stream limit, and an overall cap.
