## F6.1 [blocker] DaisyUI 5 `.alert` is display:grid, so `flex-col items-start` is inert — every multi-paragraph alert lays out as newspaper columns

File: web/src/lib/components/OutcomeAlert.svelte:33

`.alert` in daisyui 5.7.25 is `display:grid; grid-auto-flow:column; place-items:center start` (confirmed in node_modules/daisyui/components/alert.css and in the built dist CSS). `flex-col` and `items-start` are flexbox properties and do nothing to a grid container. Every alert in the app carries exactly that combination.

The built rejected capture already shows it: "Couldn't add this album" and "The album didn't pass its checks." sit side by side on one line, not stacked.

The pushed-back alert is where it becomes an embarrassment. I rendered it against the built CSS: heading, paragraph 1, paragraph 2, and the three-button div become FOUR grid columns. The main explanatory paragraph is squeezed into a ~70px column reading "MusicBrainz / didn't find a / match for / this album," — one or two words per line, twenty lines tall. This is the primary recovery screen (contract section 5B); it is unreadable.

Affected: App.svelte:356 (signed-out), :404 (preflight-rejected), :458 (upload stopped); OutcomeAlert.svelte:33, :55, :64, :73 (all four outcomes); Journey.svelte:190 (in-library), :219 (format-rejected).

Proposed fix: Replace `flex-col items-start` with DaisyUI's own `alert-vertical` (grid-auto-flow:row) plus `text-left`/`justify-items:start`, or drop `.alert` grid layout by wrapping the children in a single child div. Fix all nine sites; a unit assertion on computed grid-auto-flow would keep it fixed.

## F6.2 [major] Journey's rejected outcome drops the per-file verdict list the mockup keeps

File: web/src/lib/components/Journey.svelte:218

Mockup 5A keeps the album card with per-track rows and their chips ("01 Intro.flac / fine", "02 Summer Song.mp3 / MP3 file") visible under the calm summary sentence. ## F6.3 [major] The wake-lock toggle has no visual on/off state — only aria-pressed

File: web/src/lib/components/WakeLockBar.svelte:26

WakeLockBar.svelte:26 renders `<button class="btn btn-outline btn-sm" aria-pressed={wakeLock.on}>Keep my screen awake</button>`. The class list never changes with `wakeLock.on`, the label never changes, and there is no CSS targeting [aria-pressed] anywhere (grep across src/ and the built CSS: zero matches).

A sighted user taps it and gets no feedback whatsoever — no fill, no check, no label change. There is no way to tell whether the screen lock is armed, on the one screen where a wrong guess means walking away and having the upload pause. It is also shaped as a plain button, not a toggle, so it doesn't announce itself as stateful even before you press it.

Proposed fix: Swap classes on state (`btn-primary` when on, `btn-outline` when off) or use DaisyUI's `toggle` with a label. Whatever the form, the on state must be visible without hovering.

## F6.5 [major] Nothing on the idle page looks droppable — the dashed target only appears once a drag is already underway

File: web/src/lib/components/DropZone.svelte:106

The mockup's idle screen has a dashed-border drop panel as a standing affordance. The built page has only a centered sentence and a divider (DropZone.svelte:106-109). The dashed border exists in the codebase — DropOverlay.svelte:19-21 — but renders only while `dragDepth > 0`, i.e. after the user has already committed to the drag.

So the page claims "Drop an album anywhere on this page" while showing no boundary, no ground change, and no target. The claim is technically true (the listener is on window) but a user has to take the sentence on faith before there is any confirmation. Proposed fix: Give the idle desktop state a real bounded target — a dashed panel that contains the picker button, the way the mockup does — and keep DropOverlay as the intensified mid-drag state.

## F6.6 [major] Vertical step labels are centered against a left rail, contradicting the component's own text-left intent

## F6.7 [major] Post-upload format rejection shows only the fallback sentence, discarding per-track detail the wire carries

File: /var/home/glw907/Projects/dubplate/web/src/components/../lib/components/Journey.svelte:221

Journey's `format-rejected` view renders `{outcome?.detail || "The album didn't pass its checks."}` and nothing more. `outcome.detail` is only ever populated on the pushed-back path (internal/serve/upload.go:657), which this branch excludes by construction, so the fallback fires 100% of the time. Meanwhile `finishResponse.Files` always carries per-file verdicts with code, label, friendly, and next_step. Section 4 ratifies a fallback only "when the wire carries no detail" -- here the wire carries full detail and the page throws it away. The most likely real rejection a family member will hit (below CD quality, damaged in transit, wouldn't unpack) therefore reads as one bare sentence with no reason, no flagged track, and no way forward.

Proposed fix: Compose the section-4 body from `outcome.files` the same way App.svelte's `composeAlertBody` does over preflight verdicts, render the failing rows as FileRow `variant="verdict"` with their `{label}` chips, render one `{friendly}` + "Next: {next_step}" hint per distinct reason code, and keep "The album didn't pass its checks." strictly for an empty `files` array.

## F6.8 [major] A terminal rejection with an unparseable body chips "stopped", the word reserved for retryable transfer failures

File: /var/home/glw907/Projects/dubplate/web/src/lib/components/FileRow.svelte:52

FileRow's chip falls through to `?? 'stopped'` whenever `failureKind === 'rejected'` but `verdict` is null, which is exactly what happens when the refusal body is not the reason JSON. That is live-reachable: preCreate answers plain-text tusd errors for bad-album, unknown-collection, session-required, deferred-length (400), unknown/cross-user session (404), and session-full (409). Section 2 defines "stopped" as "transfer failed, awaiting retry", and the ratification note attached to it exists to keep a failed row from misreading its own state. Here the misread runs the other way: a permanently refused file reads as a paused one, and the "Retry" affordance it invites will fail identically every time. The neutral `badge-ghost` class it also inherits makes it look the same as "waiting" and "sending".

Proposed fix: Split the fallback by failure kind: `failureKind === 'connection'` keeps "stopped" and `badge-ghost`; `failureKind === 'rejected'` with no label chips "didn't pass" with `badge-error`. "didn't pass" matches the Label() register (one to three words, lowercase, verdict-shaped alongside "not FLAC" and "wouldn't unpack") and echoes section 4's own fallback body. Add it to the contract as section 4's label fallback, and note in section 2 that "stopped" is now connection-only.

## F6.9 [major] Journey: a failed finishSession freezes the spine at "Matching" forever with no error and no retry

File: /var/home/glw907/Projects/dubplate/web/src/lib/components/Journey.svelte:129

`runFinish()` catches every error with an empty block whose comment claims `store.signedOut` covers it. That is true only for `SignedOutError`. `finishSession` rethrows on a network drop, a 500, or a non-JSON body. In that case `outcome` stays `null`, `finishing` becomes `false`, and `viewMode` (line 61-64) returns `'finishing'` permanently — `statuses` is `['complete','complete','current','upcoming']`, so step 3 "Matching / checking MusicBrainz, just a moment" pulses indefinitely. `announceForViewMode()` hits `default:` and says nothing. `retryFinish` is only reachable through `OutcomeAlert`'s `probe-unavailable` branch, which requires an `outcome`, so there is no recovery path short of a page reload.

Journey.test.ts covers the pushed-back, matched, in-library, and still-resolving cases; there is no test for a rejecting `finishSession`.

Proposed fix: Add a `finishError` state set in the `catch` (skipping it when `store.signedOut` is already true), a `'finish-failed'` `ViewMode` mapped to `['complete','complete','error','upcoming']`, and render the existing `probe-unavailable`-shaped alert with `onTryAgain: retryFinish`. Add a test that makes the fake store's `finishSession` reject and asserts a retry control appears.

## F6.10 [major] Journey starts a 5s poll from a `finally` block that can run after the component is destroyed, leaking an uncleared setInterval

File: /var/home/glw907/Projects/dubplate/web/src/lib/components/Journey.svelte:124

`onDestroy` runs `stopPolling?.()`, but `stopPolling` is only assigned in `runFinish`'s `finally` (line 141), which resolves asynchronously. `finishSession` blocks server-side until the outcome is decided, so the window is wide.

Sequence: Journey mounts and awaits `finishSession` → the user taps "Your uploads" in the header (App.svelte:325), flipping `view = 'history'`, which is the first `{#if}` branch and unmounts Journey → `onDestroy` calls `stopPolling?.()` on a still-null value → `finishSession` resolves → the `finally` runs `store.startJourneyPolling(sessionId)` on the destroyed component. Nothing ever calls the returned stop function, so `/api/journey/<id>` is fetched every 5 seconds for the rest of the page's life. The same `finally` also calls `announceForViewMode()`, writing an outcome announcement for an unmounted view into App's shared live region while the user is reading History.

(Remounting Journey happens to clear the orphan, since `startJourneyPolling` calls `stopJourneyPolling()` first — but only if the user navigates back.)

Proposed fix: Track destruction and bail: `let destroyed = false; onDestroy(() => { destroyed = true; stopPolling?.(); void wakeLock.release(); });` then guard the `finally` body with `if (destroyed) { return; }`. Better still, drive polling from an `$effect` keyed on `outcome?.promoted` and `sessionId` and return `store.stopJourneyPolling` as the effect's teardown, which Svelte guarantees runs on unmount (https://svelte.dev/docs/svelte/$effect#Understanding-lifecycle).

## F6.11 [major] No way to upload a second album after a successful one without reloading the page

File: /var/home/glw907/Projects/dubplate/web/src/lib/components/Journey.svelte:189

The `in-library` success card renders only a heading, the album title, and "Open in Navidrome". `App.phase` is still `'uploading'` and nothing resets it. The header's only control toggles between upload and history (App.svelte:325), and returning from history lands back on the same success card. `resetSelection` is reachable only through `onFixNames`, which is wired to the pushed-back and preflight-rejected branches. A contributor who successfully adds one album and wants to add another has to reload.

Proposed fix: Add an `onDone`/`onUploadAnother` callback prop to `Journey`, render an "Upload another album" button on the `in-library` card, and wire it in App.svelte to `resetSelection()` (which per the first finding should also reset the store's session state).

## F6.12 [major] History uses a `disabled` button as every non-pushed-back album title, and the disclosure has no aria-expanded

File: /var/home/glw907/Projects/dubplate/web/src/lib/components/History.svelte:102

Every row's album title is a `<button>` with `disabled={!isPushedBack(row.state)}` and `onclick={() => isPushedBack(row.state) && toggleExpanded(row)}`. For the common cases (`in-library`, `uploading`, `checking`) that renders a disabled button: removed from the tab order, announced by screen readers as "<album>, dimmed button", and rendered by DaisyUI/Tailwind at reduced opacity — so the album name, the row's primary content, reads as unavailable.

When it *is* enabled it is an unlabeled disclosure: no `aria-expanded`, no `aria-controls`, so a screen-reader user gets no signal that activating it reveals the OutcomeAlert below, nor that it is currently open.

Proposed fix: Render a plain `<span class="min-w-0 flex-1 truncate">{row.album || 'Untitled album'}</span>` for non-pushed-back rows and only emit a `<button>` for the pushed-back/probe-unavailable rows (an `{#if isPushedBack(row.state)}` split, not a `disabled` attribute). On that button add `aria-expanded={expandedSessionId === row.sessionId}` and `aria-controls={`history-detail-${row.sessionId}`}`, with the matching `id` on the OutcomeAlert wrapper at line 121.

## F6.13 [major] NAMED CHECK 3 — contrast: the nested opacity in FileRow drops helper text to 3.6:1 (dark) / 2.7:1 (light), below 1.4.3

File: /var/home/glw907/Projects/dubplate/web/src/lib/components/FileRow.svelte:68

`FileRow.svelte:67-69` nests an element-opacity utility inside an already-alpha'd text color:

    <p class="text-base-content/60 text-xs">
      {formatBytes(ackedBytes)} confirmed <span class="opacity-70">of {formatBytes(size)}</span>
    </p>

The `/60` color modifier and the `opacity-70` on the span multiply: effective alpha 0.42. Computed against the theme's own oklch values:
- dark, base-content over base-100: **3.64:1**
- light, base-content over base-100: **2.71:1**
The text is `text-xs` (12px), so the required ratio is 4.5:1 (1.4.3, AA). Both themes fail, the light theme badly. This is the live per-file byte readout during the transfer — the honest-progress copy that is the whole point of the row.

CLEAN on the rest of this check, computed the same way (oklch -> sRGB, alpha composited over the surface):
- `text-base-content/70` (App.svelte:362, 454; DropZone:107; SpecCard:31): dark 7.49:1, light 6.70:1. PASS.
- `text-base-content/60` used alone (App.svelte:378, 388, 467; JourneySteps:78; History:96; WakeLockBar:23; FileRow:65): dark 5.89:1, light 4.73:1. PASS, but the light theme sits only 0.23 above the 4.5 line for 12-14px text — a later tweak to base-content or base-100 breaks it silently.
- Chip labels: currently base-content on base-100 (see the blocker above), so they pass by accident; re-check every chip after the semantic tokens are defined, since that is exactly where color-pair contrast usually breaks.
- `btn-primary` surface vs page: dark 9.94:1, light 7.83:1. Primary-content on primary: dark 11.56:1, light 7.38:1. PASS.

Proposed fix: Drop the nested `opacity-70` and let the whole line sit at `text-base-content/60`, or if the two halves need visual separation, raise the parent to `text-base-content/80` and use `/60` on the inner span (dark 5.89:1, light 4.73:1). Never compose a color-alpha modifier with an element `opacity-*` utility on text.

## F6.14 [major] The <progress> bar has no accessible name

File: /var/home/glw907/Projects/dubplate/web/src/lib/components/FileRow.svelte:70

`FileRow.svelte:70` renders `<progress class="progress progress-primary w-full" value={progressBytes} max={size}>` with no `aria-label`, no `aria-labelledby`, and no wrapping label. `<progress>` maps to `role="progressbar"`, which requires an accessible name; a screen reader announces it as an unnamed "progress bar, 43 percent" with nothing tying it to the file it belongs to. In a multi-file album selection there are N of these in a row, all identical and all anonymous. WCAG 1.1.1 / 4.1.2.

Secondary: `value` and `max` are raw byte counts, so the announced percentage derives from the *transferred* figure while the visible text beside it reports the *server-acknowledged* figure. The two readings disagree by design (the store's honest-progress split), which is confusing when heard rather than seen.

Proposed fix: Add `aria-label={`Upload progress for ${name}`}` to the `<progress>` element. Consider `aria-valuetext` carrying the acked figure so the spoken value matches the visible "N confirmed of M" text rather than the raw transfer count.

## F6.15 [major] History's disclosure button has no aria-expanded / aria-controls, and non-expandable rows are disabled buttons

File: /var/home/glw907/Projects/dubplate/web/src/lib/components/History.svelte:102

`History.svelte:102-109` renders the album title as a `<button>` for every row. Two problems:

1. For pushed-back and probe-unavailable rows the button is a disclosure that toggles `expandedSessionId` and reveals an `OutcomeAlert` below (History.svelte:121-133). It carries no `aria-expanded` and no `aria-controls`. A screen-reader user is told "button" with no indication that it expands anything, and gets no state feedback after activating it. WCAG 4.1.2 Name, Role, Value.

2. For every other state the same element is a `<button disabled>` whose click handler short-circuits. A disabled button is a control announced (or skipped) as an unavailable control; the album title here is not a control at all, it is content. AT users hear "Field Recordings Vol 1, button, unavailable" for a row that has nothing to activate. WCAG 1.3.1 / 4.1.2.

Proposed fix: Render the title as a plain `<span class="min-w-0 flex-1 truncate">` when `!isPushedBack(row.state)`, and as a real disclosure button when it is: add `aria-expanded={expandedSessionId === row.sessionId}` and `aria-controls={`row-detail-${row.sessionId}`}`, with the matching `id` on the revealed OutcomeAlert wrapper. A visible caret or chevron that rotates on expand would also fix the fact that expandability is currently signalled only by the `link` underline.


## Standing mandate: idiomatic Svelte 5 / DaisyUI 5 (Geoff, 2026-09-01)

Push hard toward idiomatic Svelte 5 and DaisyUI 5 while folding, and treat
un-idiomatic code you touch as in scope:

- DaisyUI first: reach for the component class and its documented modifiers
  (alert, badge, steps, btn sizes, card, list) before hand-rolled utility
  stacks. Never fight a component's own layout model (the .alert grid
  finding is the canonical example). Colors come from theme tokens, never
  hardcoded values.
- Svelte 5 runes idiom: $derived for derived values (never an $effect that
  mirrors state), $effect only for real side effects with cleanup returned,
  $props() destructuring with typed defaults, callback props over
  createEventDispatcher, snippets over slots.
- If the idiomatic shape and a finding's proposed fix conflict, the
  idiomatic shape wins; note the divergence in your return.

Exemplar (Geoff, 2026-09-01): the cairn UI work is the reference for what
idiomatic looks like on this stack. Before writing component code, skim
two or three files under

ExpandableRow, EmptyState, PageHeader) and
/var/home/glw907/Projects/cairn-cms/src/lib/components/ and imitate their
