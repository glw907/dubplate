# F4: Theme: semantic colors, light theme, ghost buttons

Each finding below is confirmed by an adversarial verifier (or by the conductor directly). Fold every one. Severity blocker findings are non-negotiable; majors may be adapted if the fix text conflicts with the code, but the defect must end up fixed.

## F4.1 [blocker] Every semantic color token is undefined — errors, successes, and warnings all render as the same neutral gray

File: web/src/app.css:33

Both themes in web/src/app.css define only base/primary/secondary/neutral. They define no --color-error, --color-success, --color-warning, --color-info (verified: `grep '--color-error:' dist/assets/*.css` returns nothing). DaisyUI's `.alert-error{--alert-color:var(--color-error)}` therefore computes to guaranteed-invalid, the `var(--alert-color, var(--color-base-200))` fallback fires, and every alert paints base-200 — the exact same fill as the SpecCard sitting above it. Same for `.badge-success/-error/-warning` and `.step-success/-error`.

Proven three ways: (a) the built rejected capture — "Couldn't add this album" is a flat gray box with a hairline border, visually identical to the format panel; (b) the history capture — "wrong format", "needs a look", and "in library" chips are all the same gray, and the *failure* chip is the least visible of the three; (c) a probe page against the built CSS (dist/assets/index-IQcOmWuR.css) rendering alert-error / alert-warning / alert-success / all four badges — every one came out identical gray.

The step spine is the worst symptom: in the built capture, steps 1 (step-success ✓) and 2 (step-error !) have NO marker disc at all — the glyphs float bare on the connector line — while steps 3 and 4 ('upcoming', no color class, so they get the real base-300 default) show solid discs. The completed and failed steps are less visible than the ones that haven't happened. A family member looks at that spine and reads the failure as the least important thing on it.

The repo's own contract says reject wording is load-bearing. Shipping it in the same gray as a success chip breaks that contract visually.

Proposed fix: Add --color-error / -success / -warning / -info (and their -content pairs) to BOTH theme blocks, sourced from Navidrome's MUI palette the same way the base colors were. Then re-verify the step spine and the badge row — those two are the proof surfaces.

## F4.2 [major] The light theme ships undesigned and unreviewed — badges disappear entirely and errors are white on white

File: web/src/app.css:13

index.html sets no `data-theme` and no `<meta name="color-scheme">`, and there is no theme control in the app. `navidrome-light` is marked `--default` and `navidrome-dark` only `--prefersdark`, so the theme follows the OS. Every capture and every mockup is dark, but an iPhone in its default light mode gets the light theme.

I rendered it against the built CSS. It is not a graceful fallback: the badge row ("fine", "MP3 file", "waiting") renders as three bare words with no pill, no border, no fill — the per-file verdict chips vanish completely. The error alert is a near-white box on a white page, indistinguishable from the format card two elements above it. And the primary goes to oklch(45% 0.19 265), an indigo, versus the dark theme's oklch(85% 0.08 240) — the two themes don't even share an accent hue.

Half the family will see a page nobody has looked at.

Proposed fix: Decide deliberately: either pin `data-theme="navidrome-dark"` on <html> and ship one designed look, or fix the light theme's semantic tokens and put it through the same review as the dark one. Do not ship it by default and unexamined.

## F4.3 [major] Ghost buttons are invisible on the dark ground — two of the three push-back recovery actions don't look clickable

File: web/src/lib/components/OutcomeAlert.svelte:48

`btn-ghost` sets no background and no border, so on base-100 it renders as bare bold text. Confirmed in the probe render of the pushed-back alert: "Upload to Private Recordings" is a filled blue button, but "Fix the names and retry" and "Add it to MusicBrainz" appear as plain bold sentences with no box, no border, nothing distinguishing them from the paragraph above. Same for "Your uploads" in the masthead — in the idle capture it has no box; it only gains a visible outline in the history capture because that shot caught the focus ring.

This is an interaction-honesty failure at the point of highest user frustration: the album was pushed back, and two of the three ways out do not read as controls.

Proposed fix: Use `btn-outline` (or a bordered soft variant) for the secondary recovery actions and the nav control so they carry a visible edge on the dark ground. Reserve ghost for controls sitting on an already-tinted surface.

## F4.4 (a11y corroboration, same root cause as F4.1) [blocker] The theme never defines --color-success / -warning / -error / -info, so every status color in the app renders as neutral grey

File: /var/home/glw907/Projects/dubplate/web/src/app.css:32

`app.css` sets only base-*, primary, secondary, neutral in both `@plugin 'daisyui/theme'` blocks. DaisyUI 5's semantic classes consume tokens that are therefore never defined anywhere in the build. Verified against the built CSS (`web/dist/assets/index-*.css`): `--color-error`, `--color-success`, `--color-warning`, `--color-info` and their `-content` pairs occur 7 times each, all as `var()` reads, zero as definitions.

Consequences, each confirmed in the supplied captures:
- `.alert-error{color:var(--color-error-content);--alert-color:var(--color-error)}` -> `--alert-color` is invalid-at-computed-value-time, so `.alert`'s `background-color:var(--alert-color,var(--color-base-200))` takes the base-200 fallback and `color` unsets to inherited base-content. Every `alert-error`, `alert-warning`, `alert-info` and `alert-success` in the app renders identically to a plain neutral alert. In `rejected-journey-desktop-1440.jpg` the "Couldn't add this album" error alert is the same grey card as the format panel above it; the ratified mockup (`reference/ref-4-journey-5a-rejected.jpg`) shows it red-tinted.
- `.step-success`/`.step-error` set `--step-bg:var(--color-success|error)` -> invalid -> `.step-icon{background-color:var(--step-bg);border:1px solid var(--step-bg)}` both unset. The completed and errored step markers render with no circle at all: the same capture shows a bare floating "✓" and a bare "!" on the spine where the mockup shows filled green and red discs.
- `.badge-success|error|warning` set `--badge-color`/`--badge-fg` to the same invalid values, so every history and file-row chip collapses to the base-100/base-content default. "in library", "wrong format" and "needs a look" are visually identical in `history-desktop-1440.jpg`; the mockup (`reference/ref-6-library-history.jpg`) colors them green / red / amber.

The whole success-vs-failure visual vocabulary is dead. A family member cannot tell a rejected album from an accepted one at a glance.

Proposed fix: Add `--color-success`, `--color-success-content`, `--color-warning`, `--color-warning-content`, `--color-error`, `--color-error-content`, `--color-info`, `--color-info-content` (and `--color-accent`/`--color-accent-content` if any accent class ever lands) to BOTH the `navidrome-light` and `navidrome-dark` `@plugin 'daisyui/theme'` blocks. Pick values that clear 4.5:1 for `-content` on its own surface and 3:1 for the surface against base-100 in each theme; re-run the contrast math on the dark ground specifically, where a Material-derived green/red needs to be lightened well past its light-theme value. Then re-capture the journey and history states against the mockups.


## Standing mandate: idiomatic Svelte 5 / DaisyUI 5 (Geoff, 2026-09-01)

Push hard toward idiomatic Svelte 5 and DaisyUI 5 while folding, and treat
un-idiomatic code you touch as in scope:

- DaisyUI first: reach for the component class and its documented modifiers
  (alert, badge, steps, btn sizes, card, list) before hand-rolled utility
  stacks. Never fight a component's own layout model (the .alert grid
  finding is the canonical example). Colors come from theme tokens, never
  hardcoded values.
- Svelte 5 runes idiom: $derived for derived values (never an $effect that
  mirrors state), $effect only for real side effects with cleanup returned,
  $props() destructuring with typed defaults, callback props over
  createEventDispatcher, snippets over slots.
- If the idiomatic shape and a finding's proposed fix conflict, the
  idiomatic shape wins; note the divergence in your return.
