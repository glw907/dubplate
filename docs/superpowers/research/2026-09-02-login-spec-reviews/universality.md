# Login-spec adversarial review (universality), 2026-09-02

Read the magic-link spec in full, the organizer spec in full, plus the grounding code and config it makes claims about (`internal/serve/serve.go`, `internal/config/config.go`, `internal/config/contributors.go`, `internal/access/access.go`, `compose.yaml`, `config/cloudflared-tunnel-config.json`, `config/contributors.yaml`, `config/navidrome.toml`, `env/dubplate.env.template`), and verified Navidrome's ExtAuth contract against upstream docs.

## Ranked findings

**[Critical] Rule 2 hands `/api/*` to dubplate, which collides with the streamer's own native API — and with this spec's own SSE sentence.**
Routing rule 2 reads "The uploader path and `/api/*` (dubplate's own API) are served by dubplate, session-gated." dubplate's API is not at `/api/*`: `/var/home/glw907/Projects/dubplate/internal/serve/serve.go:80` is `const basePath = "/upload"`, and every route (`/api/session`, `/api/journey/{id}`, `/api/config`, `/files/`) is mounted beneath it by `mountBasePath`. `/api/*` is Navidrome's native SPA API — the spec names it itself two paragraphs later ("Navidrome's `/api/events`" streaming through the proxy). As written, rule 2 swallows every player API call and the web player never loads, while the spec simultaneously requires that same prefix to proxy. Rule 2 should own the uploader base path only, and API-path ownership on the streamer side is driver knowledge.

**[Critical] The trusted-source pin as worded trusts every container on the bridge, including the internet-facing cloudflared.**
"`ND_EXTAUTH_TRUSTEDSOURCES` pinned to the compose gateway CIDR the estate already pins" — the estate pins a *subnet*, `172.30.0.0/24` (`compose.yaml` `networks.default.ipam`), and cloudflared lives inside it. Pinning that /24 means anything reaching `navidrome:4533` from the bridge can assert `Remote-User` for any account, and `config/cloudflared-tunnel-config.json`'s bare `music.907.life` rule routes internet traffic straight to `navidrome:4533` today. The estate also pins no TrustedSources value at all right now, so "already pins" is false. This needs the single observed source address of serve's proxied requests, plus an explicit requirement that no other network path reaches the streamer, plus an ordering constraint that the ingress flip precedes enabling ExtAuth.

**[Critical] The design fuses three identities into the roster's `name` and leaves an adopter no field to separate them.**
"The trusted header value is the contributor's roster `name`, the same identity that names their inbox directory." `config/contributors.yaml`'s own comment states `name` IS the inbox directory name, and `internal/config/contributors.go` matches it as an exact string (`DirNameFor`). This spec promotes that one string to streamer account name and auth principal. An adopter whose existing streamer usernames differ from inbox directory names cannot express it, and renaming to fix the streamer rewrites every inbox path and every `internal/ledger` `LibraryPaths` link. The sharp edge: a roster `name` equal to the streamer's admin username silently logs that member in *as admin* — and the spec's own note ("The estate's admin account predates this change") is exactly that scenario. Needs an optional per-contributor `streamer_username` and a startup/`doctor` collision check.

**[High] Single-hostname topology is assumed throughout, and the cookie is never scoped.**
"`dubplate serve` becomes the ingress for the music hostname" and consumption "redirects to the originally requested path (validated as same-origin relative, never an absolute URL)." Split uploader and streamer onto separate hostnames — a natural adopter choice — and nothing works: a host-scoped cookie is not sent to the sibling host, a parent-`Domain` cookie appears nowhere in Config, and a relative-only redirect cannot cross hostname. The Sessions section specifies `Secure`, `HttpOnly`, `SameSite=Lax` and omits `Domain` and `Path` entirely. Either state same-origin as a hard precondition of the SSO capability, or add cookie-domain config plus a redirect-target allowlist.

**[High] The forward-auth shape — the universal deployment — is named in the constraints and then never designed.**
The universality test promises "forward-auth proxies optional in front," but Topology only ever builds serve into an `httputil.ReverseProxy`. Making serve the proxy is an artifact of *this* estate: cloudflared cannot inject auth headers and the box runs no nginx/Traefik/Caddy. Adopters who already run one need a `GET /auth/verify`-style endpoint returning the identity header, not a Go proxy — and they would not inherit the availability coupling the spec then accepts on their behalf ("serve down means the web player is down").

**[High] No amendment covers cookie-derived identity against the organizer's authorization model.**
The organizer spec states: "Admin verbs accept header-only identity assertions and reject cookie-derived identity, which preserves ROADMAP's wall against admin verbs reachable from the browser origin." This spec introduces the estate's first cookie-carrying identity and says only that "the verify-identity seam yields a verified email." Provenance is not part of what the seam yields, so the organizer's rule cannot be enforced at the seam it names. This is the missing fourth amendment: the verified identity must carry its assertion channel (cookie / header / service token).

**[High] CSRF is absent from Security requirements, in the pass that introduces the first first-party cookie.**
The list covers header stripping, rate limits, timing-safe comparison, nonces, and log hygiene, and never mentions CSRF — while the organizer spec explicitly requires "CSRF defenses scoped to cookie-carrying browsers." `SameSite=Lax` plus the existing `requireSameOrigin` (serve.go:254) may cover the uploader, but the proxy now forwards cookie-authenticated state-changing requests to the *streamer's* native API, a new cross-surface that no stated requirement addresses.

**[High] Restart-forgives-replay is argued from family scale, but the estate's own deploy cadence is the trigger.**
"serve keeps a small consumed-nonce set with TTL, which survives within a process lifetime; a restart forgiving a replay inside the 15-minute window is an accepted family-scale tradeoff." serve is a systemd unit; every `deploy.sh` run restarts it, so this is not an adopter-scale question. `DUBPLATE_STATE_DIR` (`/var/lib/musicbox`) exists precisely because the architecture requires durable, non-RuntimeDirectory state for exactly this class of file. Single-use is the whole security claim of a magic link; the durable set is the correct default.

**[High] Revocation-by-rotation plus a 90-day rolling session is a weak default, and it forecloses the device-code plan the spec promises.**
"Default lifetime 90 days, rolling" against "Revocation is secret rotation, which signs out everyone." A lost phone costs either three months of exposure or an estate-wide sign-out. The spec then asserts "the admin-spine rung later builds device-code token acquisition on the same session vocabulary" — under one shared HMAC secret, revoking one leaked device token also signs out every browser. A per-user epoch/generation is cheap now and is machinery rung 11 needs regardless.

**[Medium] Build-order task 5 mixes the universal subsystem with the estate cutover, and the cutover is the only irreversible step with no rollback named.**
"(5) Navidrome ExtAuth config + compose/tunnel rewiring + deploy.sh." Tasks 1–4 and 6 build the universal subsystem; task 5 flips the tunnel so the entire music host — native `/rest/*` included — transits serve. The organizer spec is disciplined about this ("The rung also exercises the rollback procedure above"); this spec names no revert for the ingress PUT, despite the previous ingress object being committed and re-PUT-able. Splitting the pass at that seam makes the structure express the universality claim and isolates the one step that needs a documented revert. Task 6's security review also currently runs *after* the cutover, reviewing a subsystem already live.

**[Medium] Enumeration kindness is baked into the design, argued from roster size.**
"That is a deliberate kindness-over-enumeration choice, recorded here: the roster is a handful of family addresses." Defensible as a *default*; not defensible as fixed behavior in a tool whose own universality test says "Every tunable is a threshold with a sane default." Make it a flag (kind by default). The same treatment is owed to the 90-day session and 15-minute expiry defaults, which the spec does at least mark as defaults.

**[Medium] Two config fields will describe the streamer's address with different semantics; the spec resolves neither.**
Config adds a driver "proxy target" and never mentions `DUBPLATE_PUBLIC_NAVIDROME_URL` (`ServeConfig.PublicNavidromeURL`, documented as "the externally reachable Navidrome address the journey UI links into"). Under the new topology the player is same-origin, so that field is now redundant, or now constrained to equal the serve origin, or now the thing that silently breaks. Its retirement or restatement belongs beside the Access retirement.

**[Medium] Access retires from the wall with no enable flag — the half-configured state the wall exists to prevent.**
"Retired from the wall: `DUBPLATE_ACCESS_TEAM_DOMAIN`, `DUBPLATE_ACCESS_AUD` (the seam keeps optional support for a forward-auth front...)." The organizer's rule: "The required-no-defaults config wall applies to what the server owns; integrations get explicit enable flags." Access becomes an integration, so it needs the flag, and the flag must make both vars required-when-enabled. Two silently-optional correlated vars is a live footgun for the adopter who sets one.

**[Medium] The verify-identity seam is written in the present tense and does not exist; the organizer assigns building it to rung 11.**
"The uploader's existing identity plumbing consumes the session the same way it consumed the Access JWT: the verify-identity seam yields a verified email." `internal/access` exposes a concrete `*access.Verifier` with `Verify(ctx, token) (string, error)`, constructed directly at `internal/serve/serve.go:242`, with `Cf-Access-Jwt-Assertion` a serve constant at line 303. No interface exists. The organizer spec assigns exactly this: "Generalizing today's Access coupling into this seam, non-browser token acquisition included, is a deliverable of the admin-spine rung." Either fund the seam here as named work, or file the amendment that moves it — currently it is neither.

**[Medium] Driver provisioning choreography is stated as core behavior, and a privilege-escalation ordering hazard is parked in a runbook.**
"the post-login redirect deliberately lands on the player root so auto-creation fires" makes a core redirect target load-bearing for one driver's auto-provisioning; a driver without auto-create needs an explicit provisioning verb instead. And "the first-user-becomes-admin rule is already spent; the runbook documents that ordering for fresh adopters" — Navidrome's docs state it flatly ("The first user created in a fresh installation, whether through externalized authentication or direct login, will always be an admin user"). A fresh adopter who enables SSO before creating an admin hands admin to whoever logs in first. That is a `dubplate doctor` preflight, not a runbook sentence.

**[Medium] The bypass path set sits in core routing while the header name sits with the driver; they are one fact set.**
Rule 1 hardcodes `/rest/*` and `/share/*` (correct for Navidrome/Subsonic, per upstream). The spec puts the header name and injection rules with the driver but leaves the bypass paths, the SSE path, and the player-root redirect in the core routing table. All four are the same driver's knowledge and should be declared together by the driver.

**[Low] `ExtAuth.LogoutURL` is unaddressed, so logout is half-wired.**
Navidrome exposes `ExtAuth.LogoutURL` to point its logout control at the external provider. Rule 3 lists a dubplate logout endpoint but never wires the streamer's logout to it, so a member logging out in the player lands on the streamer's own login page with the dubplate session cookie still live, and the next click re-SSOs them. Belongs in the driver config list beside the header name.

**[Low] The universality test names a rule the repo already breaks, and the new login page is the next breach point.**
"No hostname, path, email, or personal name outside `internal/config`." `config/navidrome.toml` carries `UIWelcomeMessage = "Wright Family Music Server"`, committed. The login page is a new Go template with site-facing copy; the spec covers contact copy but not the masthead, where `SiteName` (already on `/api/config` explicitly "so the adopter goal holds") is the existing answer. Say so, and either fold the toml under the rule or grant it a stated exception.

**[Low] "One compact pass" understates the work and omits the required plan-header discipline.**
Six tasks, an attended gate, then U12b's FileBrowser cutover, the Access application deletions, and two pass closes running unattended on one yes. Six tasks is the workflow-mode threshold, and the pass header owes a token ceiling and checkpoint interval. Neither appears.

## The three I would fix first

1. **The `/api/*` collision (Critical #1).** It is a hard functional break — the player will not load — it contradicts a sentence in the same section, and the fix is one routing-rule rewrite before anyone builds against it.
2. **The trusted-source pin (Critical #2).** It is the one finding that turns into a live impersonation hole on the production box, it rests on a false premise about what the estate "already pins," and it carries an ordering constraint (ingress flip before ExtAuth enable) that task 5 currently does not state.
3. **The roster-`name` fusion (Critical #3).** It is the finding the owner's constraint is actually about: one string doing filesystem, streamer-account, and auth-principal duty, unfixable by an adopter without rewriting their library paths — and in the estate's own configuration it is one string collision away from silently granting admin.
