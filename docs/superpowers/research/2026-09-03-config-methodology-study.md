# Configuration methodology study

Dispatched 2026-09-03 (Geoff, evening session): why beets configuration
hurts, which mechanisms from admired tools transfer, and six suggestions
(S1-S6) with rung placements. Constraint honored throughout: rung 10's
layout-parity bar fixes the template DSL itself; elegance comes from the
layer around it. Feeds the organizing-engine rung spec alongside the
organization config survey of the same date.

---

I read the two specs, `internal/config/`, and the doctor/check scaffolds, then researched beets' config surface and comparison tools. Findings below.

## One constraint that shapes everything

Rung 10 requires layout parity: "layout-parity fixtures proving the beets path-format DSL and query-prefixed collection routing reproduce the estate's computed paths — engine work, because any beets-migrating adopter faces the same question," plus a corpus-driven path-parity diff. The template DSL is therefore fixed by the parity bar. Elegance has to come from the layer around the DSL, not from inventing a better one. Every suggestion below respects that.

---

## (a) Why beets config is hard, ranked by harm to stranger setup

**1. There is no config-time validation, by construction.** Confuse validates lazily at access time (`config['num_goats'].get(int)`), so a key nobody reads is never checked, and a typo'd or duplicated key cannot be detected in principle. A user on the beets forum had `paths:` defined twice; the second silently won, `beet config` showed the defaults, and he diagnosed it himself with "I'm a goofball. I had `paths:` twice." Two open requests name the gap directly: [#6218 "Config Validator"](https://github.com/beetbox/beets/issues/6218) (Dec 2025) asks for validation against a known-issues document, and [#5971 "Autogenerate config file with schema"](https://github.com/beetbox/beets/issues/5971) (Aug 2025) asks for a YAML schema so an editor LSP can catch errors. Neither exists. This is the root pain; most items below are its symptoms.

**2. Path templates fail silently and render the failure into the filesystem.** The docs are explicit: "If a value or function is undefined, the syntax is simply left unreplaced. For example, if you write `$foo` in a path template, this will yield `$foo` in the resulting paths because 'foo' is not a valid field name." A typo produces a directory literally named `$albumartst`. Worse, "if an error occurs in the Python code that implements a function, the function call will be expanded to a string that describes the exception," so a Python traceback fragment becomes part of a path. The docs also have to warn in prose that "you almost certainly want to use `$albumartist` and not `$artist`," because the near-miss is valid and splits an album across folders.

**3. You cannot see your layout until after the files have moved.** `beet import --pretend` "will just print a list of files that it would otherwise import" — source files, not destination paths. Destination preview exists only as `beet move -p`, which operates on items already in the library. So the stranger's loop is import, inspect the result, edit config, `beet move`. The first render of his own layout arrives after the commitment.

**4. Rule precedence is order-dependent, invisible, and built on a data structure that cannot carry order.** The docs: "The queries are tested in the order they appear in the configuration file, meaning that if an item matches multiple queries, beets will use the path format for the *first* matching query." [#6216](https://github.com/beetbox/beets/issues/6216) (Dec 2025) is the consequence: YAML mappings are unordered per spec, home-manager emits valid YAML with different key order, a less specific query matches first, "This causes albums to be imported into the wrong path." The filed fix is to make `paths` a list. No verb tells you which rule matched a given album.

**5. The default surface is large, implicit, and undiscoverable.** `config_default.yaml` is 206 lines with ~38 top-level keys before a single plugin loads, including a 20-entry `match.distance_weights` block and a regex `replace` map. `beet config -d` dumps merged defaults, but there is no annotated starter file: [#1677](https://github.com/beetbox/beets/issues/1677) has asked for "a config file containing all defaults and comments" since 2015 and is still open, and [#4533](https://github.com/beetbox/beets/issues/4533) asks to split the config doc into basic and advanced. Plugin options land as their own top-level keys, so the surface grows with the plugin list and no single document holds it. [#5314](https://github.com/beetbox/beets/issues/5314) records an option (`overwrite_null`) that shipped undocumented.

**6. A setting can be accepted and then do nothing in a particular verb.** This is a recurring class, not a one-off: [#6190](https://github.com/beetbox/beets/issues/6190) (`import -C` fails to override `move: yes`), [#3751](https://github.com/beetbox/beets/issues/3751) (`asciify_paths` ignored), [#5395](https://github.com/beetbox/beets/issues/5395) (`beet update` ignores `replace`), [#4518](https://github.com/beetbox/beets/issues/4518) (musicbrainz host/ratelimit options ignored), [#3064](https://github.com/beetbox/beets/issues/3064) (`match.ignored` not respected). Lazy read-site validation is what makes this class possible: an option only exists where somebody remembered to read it.

**7. Finding the config file at all.** BEETSDIR, platform default paths, and `--config` (which merges rather than replaces) combine into [#5465](https://github.com/beetbox/beets/issues/5465) ("Beet dosent recognise my config file", 11 comments) and [#5507](https://github.com/beetbox/beets/issues/5507) (XDG_CONFIG_HOME ignored).

**8. YAML itself is a poor host for template strings.** Templates must be one physical line ([#2147](https://github.com/beetbox/beets/issues/2147), open since 2016, 16 comments, asking to ignore newlines in `paths` for legibility), `yes`/`true` are ambiguous ([#4590](https://github.com/beetbox/beets/issues/4590)), and a leading `*` in a value is a YAML syntax error ([#1178](https://github.com/beetbox/beets/issues/1178)).

Your repo's own evolution study already carries the meta-lesson (U5, and the "bespoke config library" note): beets built and maintained its own config library for a decade, and its compat breaks were defended only by the changelog.

## (b) Transferable mechanisms and fit

| Mechanism | Prior art | What it buys | What it costs | Fit |
|---|---|---|---|---|
| Validate as a verb and as a gate | `caddy validate`, `nginx -t`, `sshd -t`, `promtool check config`, `docker compose config`, `systemd-analyze verify` | Errors at config time instead of run time | The validator must actually provision; Caddy documents that a config can adapt cleanly and still fail validation | Excellent. `check`/`doctor` exist, and the gate already runs two validators of this shape |
| Compile-and-show | `caddy adapt` prints the JSON a Caddyfile expands to | Convention stops being hidden; the user learns the real model | A second representation to keep honest | Excellent for presets that expand to template text |
| Effective-config dump, differences only | `postconf -n` (non-defaults) vs `postconf -d`, `sshd -T`, `nginx -T`, `git config --list --show-origin --show-scope` | Answers "what is in force and where did it come from" in one small artifact | Needs one registry of defaults | Excellent. The threshold registry is already that registry |
| Rule tracing | `git check-ignore -v` prints file, line, and pattern that decided a path | Kills first-match-wins opacity; answers beets #6216 directly | Rules need stable identity, so an ordered list rather than a map | Excellent, and the shape decision must be made before rung 9 ships |
| Dry run with a diff | `rsync -n`, `terraform plan`, `kubectl --dry-run`, `ansible --check --diff`, `rename -n`, `mmv -n`, `beet move -p` | Blast radius measured before commitment | The preview must share the real code path or it lies | Excellent. Rung 10 already mandates a no-move dry-run |
| Live template preview in the UI | Lidarr/Sonarr/Radarr naming settings: an example filename updates as you type, with a token picker | The DSL becomes learnable without docs | Needs a render endpoint plus sample records | Strong, given the embedded reference client and API-first posture |
| Tiny required set, explicit enable | Navidrome (near-zero required config, ignores invalid options and logs them), Tailscale | A stranger reaches a running system fast | Silent defaults conflict with a required-no-defaults wall | Already resolved by the wall's owned/integration split; see S4 for where it bends |
| Option minimalism as policy | Prettier: "It is *opinionated*", option requests no longer accepted | Bounded surface, docs, and tests | A real need occasionally has no knob | Strong, and it matches the settled no-plugin-ABI fork |
| Typed schema, generated docs | JSON Schema (what beets #5971 wants), CUE/Dhall, Traefik/Grafana generating reference docs from config structs | One source of truth for keys, docs, and editors | A schema language is a dependency and a second config system; the evolution study argues against exactly this | Partial. Generate the artifacts from the Go tables; skip the external language |
| Wizard | `rclone config`, Gitea and Syncthing first-run pages | The stranger never faces a blank file | A wizard is a second config writer that must satisfy the same validator, and it rots | Medium. A non-interactive `init` that prints a filled template plus doctor's verdict is cheaper |
| Preset inheritance | tsconfig `extends`, ESLint shareable configs, Caddyfile snippets | Outcome-named starting points | Hidden inheritance if the preset stays opaque | Good only when paired with compile-and-show |

## (c) Suggestions

**S1. Make the layout rule set an ordered list of named rules, and ship a trace verb.** Beets' `paths:` is a mapping used as an ordered rule list, which is the direct cause of #6216 and of the general inability to say why an album landed somewhere. dubplate should define layout as a sequence of `{name, when, template}` rules, evaluated in order, with `default` as the terminal rule, and each rule carrying a stable name. On top of that shape, `dubplate-server layout explain <album-or-query>` prints the matched rule's name and index, the query that matched, and the rendered path, in `git check-ignore -v`'s shape. The same ordered structure makes two static checks nearly free at config load: an unreachable rule (subsumed by an earlier one) and a rule whose query references an undeclared flexible attribute, which is the cheap half of what beets #6218 is asking for. This composes with the wall cleanly because the rule list is engine config selected by one wall key, and doctor reports which selection is in force. Build cost is small, because rung 9 must build the matcher and renderer regardless; the deliverable here is the data shape and the naming discipline, not new machinery. Getting the shape wrong is expensive later, since changing a map to a list after adopters have configs is a breaking change.

**S2. Compile templates at config load and refuse unknown field references.** Beets renders `$albumartst` literally into the filesystem and expands function errors into filenames. dubplate's renderer knows its field vocabulary (the store schema plus flexible attributes declared in config), so it can compile every template at load and fail with a named error: unknown field, unknown function, wrong arity. This is the template-level analogue of the wall's loud-compat rule, and it should read the same way, naming the likely intended field when the edit distance is small. Two boundaries matter. Strictness applies to field *names* at compile time, never to rendering semantics, so the rung 10 parity fixtures still reproduce beets renderings exactly for valid templates. A known field with an empty value is a different case from an unknown field name, and it stays defined behavior, with the empty case expressed explicitly through a conditional rather than falling out as an accidental empty path segment. Cost is small and it is cheapest now, since the compiler is being written at rung 9 anyway; retrofitting strictness after adopters have templates that "work" is a compat event.

**S3. Ship a preview verb that renders the configured layout before anything moves, at two scales.** `layout preview --sample` renders a built-in sample set covering the hard cases (multi-disc, various-artists compilation, singleton, non-ASCII, over-long names, two same-titled albums needing disambiguation, a collection-routed album), and `layout preview --library` reports how many files would move plus the first N moves as a diff. This replaces beets' import-then-inspect-then-`beet move` loop and its source-files-only `--pretend`. It composes with rung 10 directly, which already requires a read-only no-move diff against the live library and re-runs it as a gate at rung 16; the preview verb is that same renderer with a different sink, so the mechanism is being paid for once and used three times. The wall is untouched, and doctor gains nothing it does not already have. Cost is small to medium, concentrated in the sample album set, which then doubles as the golden fixture for layout tests and as the payload for the web UI's live preview.

**S4. Outcome-named presets that expand to visible template text, with the wall carrying the selector.** (Retired 2026-09-12 by the configuration homes spec: the selector is the layout default in the settings table and each collection row carries its own template; the presets and `layout show` survive as-is.) `DUBPLATE_LAYOUT=standard` (alongside `by-original-year`, `multi-disc-folders`, and the estate's collection-routed variant), and `layout show` prints the expansion as exactly the text a custom file would contain, in `caddy adapt`'s shape. This replaces the copy-a-config-from-a-blog culture and the blank-file problem that #1677 has been open about since 2015, and the visible expansion keeps the preset from becoming an opaque black box. Here is where I argue the wall should bend, and only here. The wall's required-no-defaults rule exists so that no adopter silently inherits site-specific values, and a layout preset carries no site-specific value at all; it is universal by construction. So the layout selector should be an owned key with a shipped, research-backed default, which is an application of the 2026-09-03 defaults-discipline ruling rather than an exception to the wall. An operator wanting custom rules points the key at a file, so there is exactly one representation and one code path. Cost is small; the presets are data and the printer is shared with S1. Freeze the roster per Prettier's argument, and require that a proposed new preset cannot be served by an existing one plus one edit.

**S5. Turn doctor into an effective-config report with origins and a differences-only mode.** Each doctor row gains where its value came from (unset default, environment, preset, file) in `git config --show-origin`'s shape, and `doctor --changed` prints only what differs from shipped defaults, in `postconf -n`'s shape. This replaces the support ritual of pasting a 200-line config where the interesting three lines are invisible, and it makes the stranger's bug report complete and small by default. It composes with existing structures rather than adding any: `Threshold` already carries key, default, and doc, `WallRow` already carries the pending status, and `rowStatuses` already parses the joined load error into per-key text. The one real addition is that `wall.get` must record provenance alongside the value, which is a field on the existing choke point. Cost is small, and it does not block rung 9.

**S6. Generate the operator-facing artifacts from the config tables, and gate that they are current.** The env manifest, the reference documentation table, and a starter layout file should all be rendered from `internal/config`'s own tables by a make target, with `scripts/check.sh` failing when the checked-in copies drift. This prevents beets' failure where documentation is the only defense (the U5 lesson) and where an option can ship undocumented entirely (#5314), and it makes CLAUDE.md's claim that `env/dubplate.env.template` is a manifest true by construction rather than by discipline. It composes with the wall exactly, since the wall is already the table; generation just gives the table a second consumer. It also gives beets' #5971 request an answer without adopting a schema language: if a JSON Schema is ever wanted for an editor, it is one more generated artifact from the same source, and no CUE or Dhall dependency enters the build. Cost is small and it fits any rung that touches doctor next.

## What belongs in the organizing-engine rung's spec

**Rung 9 (pipeline: layout and collection routing) must carry S1, S2, and S4.** All three are data-shape and load-time-contract decisions that become breaking changes once adopters have configs, and all three are nearly free while the renderer is being written. S1's ordered-list shape is the single most important of these, since it is the one beets got wrong in a way its own issue tracker has now diagnosed for you.

**S3 splits across rungs 9 and 10.** The sample-set preview belongs to rung 9, because the sample set is the layout test fixture. The library-scale preview belongs to rung 10, which already specifies the no-move dry-run and the corpus path-parity diff; specify it there as the same renderer behind a preview sink, so it is not built twice.

**S5 and S6 are doctor and gate work, not engine work.** Neither blocks rung 9, and both can ride whichever rung next touches `cmd/dubplate-server` or `scripts/check.sh`. S5's provenance field is worth landing before rung 5 adds the identity-source selector, since that is when the wall first has multiple plausible sources for one value.

**The live-preview settings page is web work that must wait for the S3 endpoint.** Lidarr's naming screen is the right reference, and the rung-7 or rung-13 surface should call the same render endpoint the CLI uses rather than reimplementing token expansion in TypeScript.
