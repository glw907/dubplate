# Adversarial review (architecture), 2026-09-01, opus agent

I've read the spec in full, plus the ROADMAP, the corpus research, the uploader spec (including its 2026-09-01 journey addendum), and the current `internal/beets`, `internal/importer`, `internal/journey`, `internal/ledger`, `internal/config`, and `cmd/dubplate/beet.go`. Findings ranked, most severe first.

---

## [blocker] There is no tag-I/O layer in the ladder, and pure-Go tag *writing* at MediaFile quality is the initiative's real core

The spec's only mention of native-dependency policy is "pure-Go core; chromaprint and ffmpeg remain optional subprocess probes... No cgo," and rung 4 lists "tag hygiene" as a plugin. But an autotagger's primary side effect is writing tags and moving files, and beets does that through MediaFile, a roughly 3000-line format-mapping layer over Mutagen that has absorbed fifteen years of real-world broken files: ID3v2.3-vs-2.4 frame semantics, TXXX vs `----:com.apple.iTunes` vs plain Vorbis comments for the ~30 MusicBrainz extended tags, `METADATA_BLOCK_PICTURE` base64 art, APEv2 leftovers, multi-valued fields, latin-1/UTF-16 legacy encodings, padding preservation, and preserving frames it does not understand. Go's ecosystem does not have an equivalent: `dhowden/tag` is a reader only, `bogem/id3v2` covers a subset of ID3v2.3/2.4 frames and rewrites the whole tag, `go-flac`/`flacvorbis`/`flacpicture` are thin and lightly maintained, and Vorbis-in-Ogg and MP4 writing are effectively unserved. Rung 3 ("pipeline port") silently depends on this layer existing and neither budgets nor names it, so the point-of-no-return rung is scheduled on top of an unscoped subsystem. *Dissolves if* the initiative restricts the engine to FLAC only, matching today's gate policy (`AllowedExt: []string{".flac"}`) and says so as a settled fork; it does not dissolve for the local-organizer product, whose laptop libraries are mixed-format. The mitigation the spec never considers is a WASM-compiled taglib driven through wazero (the `go-taglib`/gonic approach), which satisfies "no cgo" and "static binary" while buying the mature implementation.

## [blocker] The conformance harness has no config oracle, and beets verdicts are a pure function of config

Each case is defined as "a self-contained triple: matcher input, frozen MusicBrainz response, expected beets verdict," and the runner drives "pinned-version beets as a subprocess." Version is pinned; configuration is never mentioned, in the spec or in the research doc. A beets verdict is determined by `match.strong_rec_thresh`, `medium_rec_thresh`, `rec_gap_thresh`, `max_rec` per-penalty overrides, the ~19-entry `match.distance_weights` table, `match.preferred` (countries, media, original_year), `match.ignored`/`required`/`ignored_media`, and any plugin registering an `album_distance` hook. Change one weight and the same input flips from confident-match to ask. So the triple is underdetermined: "expected beets verdict" is meaningless without naming the config that produced it, the corpus must be parameterized by config or explicitly pinned to one, and the Go matcher must reimplement the entire tunable surface rather than "the distance and penalty model" as rung 2 states. This also forks against a stated product goal: conformance proven against the estate's `config/beets-config.yaml` says nothing about the stranger-adopter's config, and conformance against stock beets says nothing about the box.

## [blocker] Rung 3 bundles four deliverables plus the irreversible production cutover, with no shadow period and no rollback

"Store, migrator, pipeline port, and the one-seam swap on the box. The initiative's point of no return, taken only on rung 2's proof." Rung 2's proof is a 150-to-300-case offline corpus, which is the only evidence gating a one-way production change to the family's library. The moment the migrator runs and the Go store becomes authoritative, reverting to beets means the beets database is stale by every import since, so "point of no return" is literal and unguarded. The obviously missing rung sits between 2 and 3: run the Go matcher in shadow on the live box against real uploads with beets still deciding, log both verdicts, and compare on the estate's actual config and actual contributor material. That shadow rung is also the only thing that tests the matcher against real traffic rather than a curated corpus, and it costs nothing irreversible.

## [blocker] The ops interface has no vocabulary for long-running work, progress, or cancellation, which is exactly where local and remote diverge

`ops` is specified as "a Go interface (import, resolve ask, history, review queue, doctor) plus request and response types. The types are JSON-serializable and are the API's wire types." An import takes minutes (the uploader spec says so outright), the uploader's own settled ruling is that "polling is the contract, a live stream is the enhancement" because cloudflared has documented event-stream buffering and a roughly 100-second idle cut, and a bubbletea TUI is worthless without live progress. `ops/local` gets progress for free from a channel or callback, neither of which is JSON-serializable; `ops/client` over the same tunnel cannot have it without a job-handle model with IDs, poll endpoints, and cancel verbs that the spec never introduces. Cancellation has the same shape: `ctx` cancellation works in-process and needs an explicit remote op. Adding the job model later is not additive, because it changes the signature of the interface's most important operation, so this must be decided before rung 5 designs `ops` around request/response.

## [blocker] Interactive ask-resolution is not a capability asymmetry, it is a different operation, and the escape hatch makes the parity suite unfalsifiable

The spec claims parity is "enforced, not hoped for: one contract-test suite runs against both implementations... so an operation added to one side fails the suite until the other side has it," then immediately declares "interactive ask-resolution is local; the review queue represents it remotely." Those two sentences cancel. An interactive matcher session is a stateful conversation with the import held mid-flight: present candidates, take a choice or a manual MBID or an edit, recompute, repeat, per album across a batch. Representing that remotely requires suspending the import as a durable, resumable, timeout-bearing server-side state machine, which is a substantially different design from a local callback, so `resolve ask` is two operations wearing one name and the contract suite cannot exercise it symmetrically. Worse, the capability-declaration mechanism gives any future operation a way to opt out of parity by declaration, and the spec sets no rule for who may declare one; the guardrail is self-disarming. And "the TUI consumes only the `ops` interface and cannot tell local from remote" is falsified by its own capability discovery, since the TUI must carry an interactive-matcher screen that has no remote analogue.

## [major] Publish-only has no answer for custody after publish, and the local album's fate is undefined

"The local organizer publishes a finished album to a server through the same validated intake API as every other client, so the server's custody guarantees hold because everything enters through the one gate." The album is already finished locally: matched, tagged, renamed, in the local store. The server then re-runs its own intake, its own matcher, its own config, against MusicBrainz data at a different time, and may pick a different release, so the same album now exists in two libraries with divergent metadata and layout. The spec never says whether the local files are kept, moved, or deleted, so a laptop-to-VPS workflow silently doubles disk. The local store carries no publish provenance, so a re-publish is indistinguishable from a first publish and only the server-side duplicates plugin stands between the family and a double admission. And the uploader's settled custody policy is push-back, not review, so a server rejection of an album the user already has organized locally is a real outcome with no defined local record. The spec designs a `remote-origin` notion for the deferred mirror while leaving the direction it actually builds unmodeled.

## [major] `restore` is a second gate, which contradicts "everything enters through the one gate"

Both binaries' subcommand rosters include `restore`, and the ROADMAP records the settled position that "migration between rungs is backup/restore... local-to-VPS is backup-from-laptop, restore-to-box." Restore replaces the library and store wholesale without touching intake, so the custody argument for publish-only ("the server's custody guarantees hold because everything enters through the one gate") is already false by the spec's own subcommand list. Either restore is admin-only and out of the custody claim, which the spec should say, or the claim needs weakening. This matters beyond wording: if restore across binaries is supported, the two binaries must keep a compatible store format across independently released versions, which is a skew problem the spec addresses only for the HTTP contract ("documented and versioned") and never for the store.

## [major] The roadmap-revisions list omits the one revision that contradicts a settled ROADMAP claim

The spec enumerates three revisions to fold into ROADMAP.md: streamer peers, client-agnostic API, and publish-only sync. The ROADMAP currently states "migration between rungs is backup/restore (T10b already frames restore as the adopter's path)" as a settled early decision, and the spec replaces it with publish-through-intake without listing that replacement. A reader of ROADMAP.md after the fold will hold both positions. Add it to the revisions list, or state explicitly that backup/restore remains the bulk-migration path and publish is the per-album path, which is probably the truth and is a cleaner story anyway.

## [major] Retiring `beet` deletes the estate's entire manual-repair surface, and nothing is named to replace it

The subcommand roster carries "`beet` passthrough until the seam swaps," and after the swap it is gone. Today that passthrough is the admin's whole ad-hoc toolkit: `beet modify`, `beet move`, `beet ls`, `beet write`, `beet update`, `beet remove`, plus every plugin command, all serialized correctly against the import lock by `runBeet`'s acquire-then-`syscall.Exec` with `FD_CLOEXEC` cleared. The spec's replacement is "browse the library, import with interactive ask-resolution, triage duplicates, run hygiene tools," which is a fraction of that surface and arrives at rung 5, two rungs *after* the swap that removes the old one. So rung 3 ships a production system where the admin's only repair path for a mis-tagged album is editing SQLite by hand. Name the replacement surface as a rung-3 deliverable, or keep beets installed as a read-write escape hatch against the same library files past the swap.

## [major] The migrator's failure modes are named at the wrong altitude, and several silently corrupt

"A one-shot converter reads the live beets database (items, albums, flexible attributes) into the Go store, so import history and collection routing survive the swap." Concrete things that do not survive that description: beets stores `items.path` and `albums.artpath` as BLOB rather than TEXT precisely so non-UTF8 filenames survive, and the corpus deliberately includes non-Latin scripts, so a migrator (or the existing sqlite3-CLI habit in `ResolveLibraryPaths`) that treats path as a string mangles exactly the material this estate expects. beets has no import-history table at all, so what actually survives is current library state with `added` timestamps; the estate's real per-session history lives in `internal/ledger`, whose `LibraryPaths` are beets-database paths, and the spec never mentions reconciling the ledger, so every contributor's journey history breaks its links at the swap. Singletons carry `album_id` NULL rather than 0. And the largest one: the on-disk layout is the real artifact, so if the Go pipeline's path formats differ from `config/beets-config.yaml`'s query-prefixed formats by one character, the first post-swap run can re-lay-out the entire library. Rung 3 needs an explicit no-move assertion and a dry-run diff of computed paths against actual paths before anything writes.

## [major] "Fully functional with no streamer configured" is false against the settled journey and the current config wall

The spec says the server "is fully functional with no streamer configured, degrading the journey's final step to 'imported, scan pending' honesty." In the shipped code, `ledger.StateInLibrary` is appended only by `journey.AdvanceInLibrary`, which requires a successful Navidrome `getScanStatus` confirming a scan completed after `StateTagging`; `BuildLibraryLink` builds a Navidrome deep link; and `DUBPLATE_NAVIDROME_URL`, `_ADMIN_USER`, `_ADMIN_PASSWORD`, `_DB`, and `PUBLIC_NAVIDROME_URL` are all `require()`d with no default. So "no streamer" is a config-wall change plus a terminal-state change to a journey the uploader pass just ratified and built, and none of that is scoped anywhere in the ladder. Separately, "scan pending" is dishonest copy by construction: with no streamer nothing is pending, ever, and the honest state is "imported, no player configured." Finally the claim inverts the stated product essence, since a server feeding no streamer is a write-only drop box for a group whose whole purpose the ROADMAP defines as "a shared Navidrome server."

## [major] "Navidrome, Jellyfin, and generic Subsonic are equal peers" does not survive the seam's own capability list

The seam is defined as "scan trigger, scan status, album deep link, capability discovery." Generic Subsonic gives you `startScan` and `getScanStatus` (API 1.15, and many servers do not implement them), and has no album deep link at all, because Subsonic is an API with no defined web UI, so the deep link that makes the journey's terminal state meaningful is Navidrome-specific. Jellyfin is not Subsonic; it has its own API with an asynchronous `/Library/Refresh` and no scan-status equivalent. The collection picker's meaning is also Navidrome-specific, since the uploader spec grounds it in "Navidrome ≥0.58 multi-library maps collections to library-root subtrees." So the peers satisfy roughly one and a half of four capabilities, "equal peers" and "reference driver, richest integration" contradict each other in the same bullet, and rung 6 builds two drivers for a family estate that runs Navidrome with no demand test. This is the accretion-by-adjacency pattern: define the seam now, ship the reference driver, and let a second driver earn its build.

## [major] The uploader's synchronous match probe has already widened the seam the spec plans to swap

The uploader spec's ratified journey addendum makes the matcher a user-facing synchronous surface: "the staged session runs the real beets matcher as a synchronous dry-run probe (seconds to a minute of MusicBrainz lookups, user present)," with the page showing "what it matched" and naming the failure with fix buttons on no confident match. `internal/beets` today has only `Import`, `ResolveLibraryPaths`, and `TriggerScan`, so that probe is unbuilt, and by the time the organizer starts, the seam will also carry a candidate-and-confidence contract derived from beets internals. That raises the conformance bar the spec sets: it is no longer enough that a batch import lands in the same place, because the user sees the candidate list and the push-back text, so the Go matcher must reproduce the *presented* candidates and their order, not just the verdict. The spec's "verdict, chosen release, distance ranking" is close to right, and should be stated as covering the probe surface explicitly.

## [major] Nothing addresses concurrency, and the ops seam multiplies writers against one flock

Today one `flock` in `/var/lib/musicbox/` serializes everything, and `dubplate beet` blocks on the same lock so an interactive session cannot race an import. The organizer adds a local TUI holding an interactive matcher session for minutes, an HTTP admin API, publish arriving from a remote client, the timer poll, `nudge-consume`, and the uploader's synchronous match probe, all against one library, and the spec never mentions the lock. A minutes-long interactive TUI session holding the import lock starves the timer and every contributor upload; not holding it means the matcher writes concurrently with an import. Rung 5 needs an explicit concurrency model, and the honest options (a per-album lease rather than a global lock, or an explicit queue with a documented starvation policy) are design decisions, not implementation details.

## [major] Putting the admin API on `serve` breaches the ROADMAP's "admin verbs stay off the browser origin" wall

The ROADMAP records, as a settled position for this very initiative, that a web admin page "earns its build only if phone triage... proves wanted in practice; until then admin verbs stay off the browser origin." Rung 6 builds "admin API spine" and the spec keeps only the *page* deferred ("The web admin page stays deferred"). Access delivers its JWT as a `CF_Authorization` cookie as well as the `Cf-Access-Jwt-Assertion` header, so an admin API served from the same origin as the contributor page is reachable by any script on that origin with ambient credentials, page or no page. That is the breach the wall was written to prevent. Either the admin API listens on a separate origin or hostname with its own Access application, or it requires a header-only bearer assertion and rejects cookie-derived identity for admin verbs, and the spec should say which.

## [major] The service-token half of the auth seam has no identity to verify

"The seam must support non-browser token acquisition (device-login and service tokens) so native clients authenticate without a cookie jar." Those two are not interchangeable. `cloudflared access login`/`token` yields a user assertion carrying `email`, which is what the ledger is keyed by, what the roster lookup uses, and what per-uploader review filing depends on. A Cloudflare Access service token authenticates a machine and its JWT carries `common_name`, not `email`, so a native client using one produces contributions attributable to nobody, and `internal/ledger`'s email key and `config.Roster.EmailFor` have no value to work with. Say that service tokens are for unattended server-to-server verbs only and that contributor-attributed operations require a user assertion.

## [major] "The review queue is the first remote job" was undercut by the uploader addendum the same day

The spec makes the review queue a headline of the server's purview and names "review-queue triage" as the TUI's first remote job. The uploader spec's 2026-09-01 addendum abolished the review path on the uploader surface: "The review path ('needs a human look', the 60-day clock, hand-tagging) is ABOLISHED on the uploader surface; the timer-driven inbox path remains as the admin-only side door." So the remote review queue now covers only material arriving through an admin-only side door, which is a fraction of the volume the queue was scoped against, and it is the sole demand argument for rung 6's remote TUI. Either name a different first remote job, or state plainly that the queue is now a low-volume admin backstop and re-argue why remote triage earns a rung.

## [major] No store schema versioning, while the spec simultaneously makes schema decisions for an unbuilt feature

The repo versions everything it persists: `importer.ReportVersion = 2`, the session sidecar's `Version`, the ledger's shape. The organizer introduces a SQLite store that evolves from rung 3 through rung 6, and the spec's only schema statement is that it "keeps a remote-origin notion so a mirror can slot in later without migration." That sentence does two wrong things at once. It admits schema evolution is a live concern while naming no migration mechanism, and it bakes a column for a feature the spec elsewhere defers, which is speculative generality that will be wrong by the time the mirror is designed. A migration mechanism costs almost nothing to add at rung 3 and makes the mirror's column unnecessary.

## [minor] The harness is described as both frozen-expectation and live-differential, and the CI cost of the second is unstated

"Each case is a self-contained triple: matcher input, frozen MusicBrainz response, expected beets verdict. A differential runner drives pinned-version beets as a subprocess and the Go matcher against the same frozen responses." If beets runs at test time the frozen verdict is redundant; if the verdict is frozen the subprocess is unnecessary. The choice has real consequences: driving beets means a pinned Python toolchain in `make check` and in CI for a repo whose gate is Go, shellcheck, vale, compose config, and `systemd-analyze`, and whose product is a static binary. Freezing verdicts means "beets changed" is invisible until a deliberate re-run. The likely right answer is both, on separate cadences: frozen verdicts in the fast gate, a live differential job on beets bumps only.

## [minor] Verdict agreement on 300 cases does not pin a continuous distance function, and tie-breaking is unspecified

The harness proves "verdict, chosen release, distance ranking." Verdict is a thresholded function of a continuous distance, so two implementations can agree on every verdict in the corpus and still differ materially in the distance they compute, which shows up the first time real material sits near a threshold. Ranking is the sharper instrument and is exactly where the adversarial stratum bites, since "near-duplicate releases (same album, different pressing/label/catalog number)" produce tied or near-tied distances, and beets breaks ties by Python's stable sort over the candidate list in the order MusicBrainz returned it. Reproducing that requires the Go matcher to preserve candidate iteration order and use a stable sort, and to compare distances numerically within an epsilon rather than only comparing ranks. State numeric distance equality as an acceptance criterion.

## [minor] The freshness triggers conflate the two axes they claim to separate, and the oracle has no exit criterion

"Freshness comes from re-capturing a rotating subset quarterly and on beets version bumps, which separates 'we differ from beets' from 'beets changed'." Re-capturing on a version bump does the opposite, because changing the frozen responses changes the inputs, so a verdict change afterward is ambiguous between new beets, new MusicBrainz data, and a matcher regression. The separation requires the two axes to move independently: a version bump runs new beets against unchanged responses, and a quarterly re-capture runs unchanged beets against new responses. Separately, the spec never says when beets stops being the oracle, or what happens the first time beets changes a behavior dubplate does not want to follow, and after rung 3 conformance to beets 2.13.1's quirks becomes a liability rather than a goal. Name the exit criterion and a divergence-acceptance procedure.

## [minor] MusicBrainz at 1 request per second is a global serialization point under a user-present synchronous probe

Rung 2 specifies a "MusicBrainz client (rate-limited, cached)" and the research notes the anonymous limit is 1 req/s. The uploader's ratified journey holds a contributor on the page for "seconds to a minute of MusicBrainz lookups," and the same limiter is shared with timer imports, the local organizer, and every other concurrent contributor. Two simultaneous uploads therefore queue behind each other with users watching. The research doc notes the limit is "higher for identified clients" and the spec drops that; registering a MusicBrainz application and a proper User-Agent, plus a documented per-caller budget under one shared limiter, should be a rung-2 requirement rather than an implementation detail.

## [minor] The ladder is not risk-ordered, and its two riskiest premises are last

"The ladder is risk-ordered." The irreversible production change is rung 3, while the two premises that would most change the design if wrong come last: whether the ops seam survives contact with a real remote implementation, and whether anyone wants the local TUI. A cheap reordering fixes it: prove the ops seam end to end with one trivial operation (`doctor` or `history`) before rung 3, which costs little and would have surfaced the job-model and asymmetry problems above while they are still cheap. Rung 5 as written carries engine extraction, the ops interface, three implementations, contract tests, the whole TUI, and publish, which is well past the four-deliverable line the workstation's own pass-sizing rule flags, and it should split.

## [minor] The engine is declared pure while today's pipeline is soaked in server concerns, and nobody owns the extraction

"`engine`: matcher, store, pipeline, plugins. A pure library that knows nothing about HTTP, terminals, or which binary hosts it." Today's `internal/importer` calls `im.Mailer.Send` in `gateAndQuarantine` and `notifySkips`, reads `im.Roster` for per-uploader emails and names, pings a dead-man's switch, files review trees by uploader and date, and stages per contributor. None of that is meaningful for a laptop with one user and no mailer, and the local binary's stated wall is "a music directory and its own state directory, nothing else." Extracting a genuinely pure engine from that is a real refactor, and the build order assigns it nowhere explicitly; it falls inside rung 5's already-oversized bundle, after the pipeline port has been written against the server's assumptions. Name notification, roster, and monitoring as engine-level optional seams at rung 3, when the pipeline is being rewritten anyway, not at rung 5 when it must be unpicked.

## [minor] "A rung that ships working but unclean has not shipped" plus "un-idiomatic code adjacent to a change is in scope" is unbounded scope with no ceiling

The Beauty and cleanliness section sets a quality bar with no budget attached, and the spec carries no token ceiling, no checkpoint interval, and no per-rung sizing anywhere. The adjacency rule in particular imports arbitrary refactoring into every rung by construction, in a repo where the shell layer is freshly retired and idiom is still settling. Additionally, "Rungs 5 and 6 touch different surfaces than rung 4 and can overlap with it once the seam has swapped" invites two executors on one repo against shared engine code, which the workstation's one-executor-per-worktree rule exists to prevent. Bound the adjacency rule (same package, same file, or reviewer-nominated) and state the overlap as sequential-with-handoff rather than concurrent.

## [minor] "Batteries-included" is claimed while two of the six named plugins are optional subprocesses

The initiative is framed as shipping "the empirically top beets plugins as built-ins: art fetch/embed, genre, duplicates, tag hygiene, fingerprinting, ReplayGain," and the build order then demotes two: "fingerprinting and ReplayGain as optional probes." On a box without chromaprint and ffmpeg, a batteries-included organizer silently loses acoustic fingerprint matching and loudness normalization, and fingerprinting's absence also changes matcher behavior relative to a beets install that has it, which the conformance corpus has no stratum for. Say plainly which batteries are in the box and which are sold separately, and either add a fingerprint-assisted stratum to the corpus or state that conformance is proven only for the no-chromaprint configuration.

## The three I would fix first

1. **Name the tag-I/O layer and settle the format scope.** Everything from rung 3 onward stands on a subsystem the spec does not acknowledge. Decide FLAC-only versus mixed-format, evaluate WASM-taglib-via-wazero as the no-cgo path to a mature implementation, and give the layer its own rung ahead of the pipeline port.

2. **Put config into the conformance triple and add a shadow rung before the swap.** A corpus case is `{input, frozen MB response, config, expected verdict}` or it proves nothing, and the only honest evidence for an irreversible production cutover is the Go matcher running in shadow against real uploads on the estate's actual config with beets still deciding.

3. **Decide the `ops` job model before the interface exists.** Long-running imports, progress, and cancellation are where local and remote genuinely differ, and the current request/response framing plus the capability-declaration escape hatch means the parity suite cannot catch it. Settle the job-handle shape, state that interactive ask-resolution is a distinct operation rather than an asymmetry of one, and set a rule for who may declare a capability asymmetry.
