## F5.1 [blocker] Desktop idle: the hint sentence is stranded between two left-aligned ragged buttons, under a centered divider that points nowhere

File: web/src/App.svelte:384

Rendered live at 1440 and 640. The block reads, top to bottom: centered "Drop an album anywhere on this page", a centered "—— or ——" divider (x 560–880), then a 148px "Choose files" button hard-left at x=400, then the sentence "One album at a time. Albums go in whole." centered on the column at x=583–857, then a 145px "Choose a folder" button back at x=400.

Three things are wrong at once. The centered "or" divider promises a centered control below it and delivers a left-aligned one. The hint sentence is centered while both buttons are left-aligned, so it belongs to neither and reads as orphaned copy. This is the first screen every family member sees. As rendered it reads as an unstyled prototype.

Proposed fix: Make the picker block one coherent group: primary button, hint directly beneath it, secondary below that, one alignment for all three. ## F5.3 [major] Touch targets: nearly every button is 32px or 40px tall, against the 44px rung the inputs already meet

File: web/src/App.svelte:325

With DaisyUI's default --size-field (.25rem): `.btn` = 40px, `.btn-sm` = 32px, `.btn-lg` = 48px. The app uses:
- `btn-ghost btn-sm` for the ONLY navigation control, "Your uploads" / "Back to upload" (App.svelte:325) — 32px, present at every width including 320.

The team clearly knows the rule — CollectionPicker's select (line 44) and every AlbumCard input carry an explicit `min-h-11`. The buttons were just missed. AlbumCard is the clearest tell: 44px inputs stacked directly above a 40px submit.

Proposed fix: Either raise --size-field in the theme so `.btn` lands at 44px, or add `min-h-11` to every button the way the inputs already have it. Drop `btn-sm` entirely on the nav and History controls.

## F5.4 [major] The tagging phase is a dead end: no way back to the picker without reloading

File: web/src/App.svelte:428

App.svelte:428 renders AlbumCard alone for `phase === 'tagging'`. AlbumCard's only action is the submit button (line 114). There is no cancel, no back, no "Try another album" — the escape hatch that every other non-idle phase gets (:427 for preflight-rejected, and Journey's outcome actions).

The same lane is reachable from OutcomeAlert's "Upload to Private Recordings" (App.svelte:219), so a pushed-back user lands here too and is then trapped.

## F5.5 [blocker] A server rejection during upload renders no heading, no reason, and no next step

File: /var/home/glw907/Projects/dubplate/web/src/App.svelte:457

Section 4's rejection copy (heading "Couldn't add this album", the count-aware body, the `{friendly}` + "Next: {next_step}" hint, "Try another album") only exists in App.svelte's `preflight-rejected` branch, which fires for exactly one reason code: bad-extension. Every server-side refusal during the transfer lands in the `uploading` branch instead, which renders an alert only for `failureKind === 'connection'`. A file refused with reject.ReasonNoSpace (507) or ReasonTooManySessions (429) gets a red row chip ("library is full" / "too many uploads") and nothing else: the ratified Friendly and NextStep strings for those reasons are marshalled onto the wire, arrive in the client, and are never rendered anywhere. The row list simply sits there with no explanation and no way forward. Since `allFilesLanded` is false, Journey never mounts either, so nothing downstream recovers.

Proposed fix: In the uploading branch, when any current file has `failureKind === 'rejected'`, render the same section-4 block the preflight branch renders: the "Couldn't add this album" alert, `composeAlertBody` over the rejected rows, one reason hint per distinct reason code from the rows' own verdicts, and "Try another album". Both branches should call one shared snippet so the two paths cannot drift.

## F5.6 [major] A failed POST /api/session leaves every row reading "waiting" forever, with no copy at all

File: /var/home/glw907/Projects/dubplate/web/src/App.svelte:153

`beginUpload` calls `void uploadStore.createSession(...).then(...)` with no catch. The store re-throws on failure, so a 429 (`reject.ReasonTooManySessions`), a 400, or a dropped connection becomes an unhandled promise rejection: `phase` stays 'uploading', `startFile` is never called, and every row sits at status 'pending' chipping "waiting" indefinitely. The user is told nothing. The ratified "too many uploads" label and its Friendly/NextStep pair are written, marshalled, and returned by the server, and on this path they can never render.

Proposed fix: Catch the rejection, decode the reason body where present, and render the section-4 alert with that reason's `{friendly}` and "Next: {next_step}". Where no reason parses, fall back to the section-2 "Upload stopped" alert with its Retry button rather than leaving the rows in a false "waiting".

## F5.7 [blocker] Store session state is never reset between uploads: a second album can finish and poll the FIRST album's session ID

File: /var/home/glw907/Projects/dubplate/web/src/App.svelte:209

`UploadStore.session` (upload.svelte.ts:358) is written in exactly one place — `createSession` — and is never cleared. `App.resetSelection()` (App.svelte:170-178) resets `phase`/`pendingFiles`/`preflightRejections` and nothing else. `journeySessionId` is `$derived.by(() => uploadStore.session.sessionId ? uploadStore.session.sessionId : sessionIdFromUploadURL(currentFiles[0].tusUploadURL))` — the store's session ID unconditionally wins.

Reachable path: upload album A as a multi-file selection (`createSession` sets `session.sessionId = A`) → A is pushed back → user clicks "Fix the names and retry" (`onFixNames = resetSelection`) → user picks album B as a single .zip → `beginUpload` takes the ZIP branch (App.svelte:146-151) which deliberately never calls `createSession` → `session.sessionId` is still A → `journeySessionId` returns A. `Journey` then POSTs `/api/session/A/finish` and polls `/api/journey/A` for album B's upload, and `journeyAlbum` (App.svelte:216, `uploadStore.session.album || ...`) shows album A's title. The family member watches album B's upload complete and is told album A is in their library.

The same root cause hits `handleResumeFilesPicked` (App.svelte:277-282): it starts the resumed files against `row.sessionId` but `journeySessionId` still prefers the stale `session.sessionId`, and `retryStalled` (App.svelte:238) builds `session_id` metadata from `uploadStore.session.sessionId ?? journeySessionId ?? ''`, so a stalled retry can be tagged with the wrong session too.

`uploadStore.journey` and `uploadStore.journeyOutcome` have the identical problem: `Journey.viewMode` reads `journey?.state` as soon as its own `outcome` resolves, so a stale `journey.state === 'in-library'` from album A renders the "In your library" success card (with A's `libraryLink`) for album B before B's first poll returns.

Proposed fix: Add an explicit `UploadStore.resetSession()` that clears `session` back to `{ sessionId: null, album: '', collection: '', state: 'uploading', detail: '' }`, sets `journey = null` and `journeyOutcome = null`, and calls `stopJourneyPolling()`. Call it from `App.resetSelection()` and at the top of `beginUpload()` (before the branch), and also from `handleResumeFilesPicked` before adopting `row.sessionId`. Separately, make `journeySessionId` prefer an explicitly-tracked session for the current selection rather than falling back to a store field that outlives it — e.g. hold a local `let currentSessionId = $state<string | null>(null)` in App.svelte, set it in `beginUpload`/`handleResumeFilesPicked`, and derive from that with the ZIP URL parse as the only fallback.

## F5.8 [blocker] A failed /api/config renders a completely blank page with no message and no retry

File: /var/home/glw907/Projects/dubplate/web/src/App.svelte:361

`onMount` runs `void uploadStore.loadConfig().then(...)` (App.svelte:93) with no `.catch`. `loadConfig` swallows only `SignedOutError`; every other failure (500, a proxy error page with a JSON content-type, malformed body, network drop) is rethrown — an unhandled promise rejection, and `uploadStore.config` stays `null`.

The template chain is `{#if view === 'history'} {:else if uploadStore.signedOut} {:else if uploadStore.config}` with **no `{:else}`** (App.svelte:343-488). So on any config failure `<main>` contains only the visually-hidden live region and the hidden resume `<input>`: the user gets the navbar and an empty page, forever, indistinguishable from "still loading". There is also no loading state on the happy path, so the two cases are the same pixels.

Proposed fix: Add an `{:else}` branch rendering an error alert with a Reload button (the same shape as the `signedOut` branch at App.svelte:356-360), and distinguish it from loading with a `let configState = $state<'loading' | 'ready' | 'failed'>('loading')`. Attach a real `.catch` to the `loadConfig()` call — `void uploadStore.loadConfig().then(...).catch(() => { configState = 'failed'; })` — so the failure is handled state rather than an unhandled rejection.

## F5.9 [major] NAMED CHECK 1 — touch targets: no button in the app reaches 44px; btn-sm targets are 32px

File: /var/home/glw907/Projects/dubplate/web/src/App.svelte:325

Measured from the built DaisyUI CSS. The theme customizes only colors, so `--size-field` keeps its 0.25rem default:

- `.btn-sm{--size:calc(var(--size-field,.25rem)*8)}` = **2rem / 32px**
- `.btn-lg` = 3rem / 48px (the only compliant control; `PickerButton` defaults to `size='lg'`)

At 32px: the masthead view toggle (`App.svelte:325` `btn btn-ghost btn-sm`), History's "Resume" (`History.svelte:112`) and "Open in Navidrome" (`History.svelte:115`), and the wake-lock toggle (`WakeLockBar.svelte:28`).

Give History's album-title disclosure `py-2.5` or `min-h-11` so the row's own tap area reaches 44px.

## F5.10 [major] NAMED CHECK 4 — keyboard: journey is fully operable, but History's Resume drops focus to <body>

File: /var/home/glw907/Projects/dubplate/web/src/App.svelte:245

VERDICT: operable, with one real focus-loss defect and one clean sub-check.

CLEAN: focus is NOT lost when the main region swaps to History. The toggle at `App.svelte:325` is in `<header>`, outside `<main>`, and persists across the swap with only its label changing, so the focused element survives. (It is silent for AT users — see the live-region finding — but focus is retained.)

CLEAN: every step of the journey is reachable without a pointer. Drag-and-drop is enhancement only — `DropZone` listens on `window` and always renders the `PickerButton` fallback, satisfying 2.5.7 Dragging Movements. `PickerButton` deliberately keeps the file input focusable (`opacity-0`, not `display:none`) and carries its own visible `focus-within` ring. `SpecCard`'s detail sheet is a native `<dialog>` opened with `showModal()`, so focus trap, Escape, and focus-return-to-invoker come from the platform.

THE DEFECT: `handleResume` (`App.svelte:245-249`) sets `view = 'upload'` first, which unmounts the entire `History` list including the "Resume" button the user just activated, and only then clicks the hidden input. The focused element is destroyed, so focus falls to `<body>`. If the user cancels the native picker — or picks files that match no anchor, in which case `handleResumeFilesPicked` returns silently at App.svelte:274-276 — they are left on the idle upload page with focus at the top of the document, no announcement, and no indication that anything happened. WCAG 2.4.3 Focus Order.

Proposed fix: Keep the History view mounted until the picker resolves, or capture `document.activeElement` before the swap and restore focus to a stable target after: move focus to `<main>` (with `tabindex="-1"`) or to the picker button, and announce the outcome through the shared live region — including the silent no-match branch at App.svelte:274, which currently fails with no user-visible feedback at all.

## F5.11 [major] <ul> elements contain <div> children, destroying list semantics for the file lists

File: /var/home/glw907/Projects/dubplate/web/src/App.svelte:412

`App.svelte:412` and `App.svelte:472` both render `<ul class="...divide-y...">` and put `<FileRow>` inside the `{#each}`. `FileRow`'s root element is a `<div>` (`FileRow.svelte:62`), not an `<li>`. HTML permits only `<li>` (and script-supporting elements) as `<ul>` children; browsers repair this by dropping the list role or by exposing a list whose children are not list items. A screen-reader user loses "list of N items" and the per-item position, which is precisely the information that makes a per-file verdict list navigable. WCAG 1.3.1 Info and Relationships.

The same nesting also doubles the separators: the `<ul>` carries `divide-y divide-base-300` and each `FileRow` carries its own `border-b border-base-300`, so every row gets two 1px lines and the last row gets a trailing rule the list should not have.

Proposed fix: Change `FileRow`'s root from `<div>` to `<li>` (it is only ever rendered inside a list at both call sites) and delete its `border-b`, letting the parent `<ul>`'s `divide-y` own the separators. If `FileRow` must stay context-neutral, wrap it in `<li>` at both call sites in App.svelte instead.

## F5.12 [major] No <h1> anywhere; the page's heading hierarchy starts at h2 or h3 depending on the phase

File: /var/home/glw907/Projects/dubplate/web/src/App.svelte:322

The masthead site name is a `<span class="text-xl font-semibold uppercase">` (`App.svelte:322-324`) — a heading element used nowhere, and heading-sized text that is not a heading. The document therefore has no `<h1>` at all. Below it, `History` opens at `<h2>` (History.svelte:93) and `AlbumCard` at `<h2 class="card-title">` (AlbumCard.svelte:62), while every alert opens at `<h3>` (App.svelte:357, 405, 459; OutcomeAlert.svelte:34, 56, 65, 74; Journey.svelte:191, 220).

In the preflight-rejected phase and in the journey's outcome states, the first and only heading on the page is an `<h3>` — two levels skipped from nothing. A screen-reader user navigating by heading (the primary way of skimming a page) gets no page title and an incoherent outline. WCAG 1.3.1 Info and Relationships.

Proposed fix: Make the masthead site name the `<h1>` (`<h1 class="text-xl font-semibold uppercase tracking-wide">`) — it already carries the right visual weight and is the page's true title. Then demote the alert headings from `<h3>` to `<h2>` so the outline reads h1 -> h2 with no gaps in every phase.

## F5.13 [major] "Upload to Private Recordings" from History leads to an empty tag form and a zero-file upload

File: /var/home/glw907/Projects/dubplate/web/src/App.svelte:346

`App.svelte:346-349` wires History's `onUploadPrivate` to `retryAsPrivateCollection()`. That function (App.svelte:219-231) derives the tag form's rows from `pendingFiles`, the in-memory selection from the *current* session. A History row is by definition a past session — after a reload `pendingFiles` is `[]`, and even without one it holds whatever the user last picked, not the row's files.

So the path renders `AlbumCard` with zero track rows, and `submitTagForm` -> `beginUpload([])` -> `createSession(album, collection, 0)` with an empty `uploadFileIds`. `allFilesLanded` requires `currentFiles.length > 0`, so `Journey` never mounts either: the user lands on a permanently blank uploading phase with no error, no progress, and no way back except the masthead toggle. This is reachable by expanding any pushed-back row in "Your uploads" and pressing the primary action — the single most likely recovery path a family member takes.

Outside strict a11y scope, but it breaks the "whole journey operable" criterion and would embarrass in front of a user.

Proposed fix: Route History's pushed-back re-upload through the same re-pick flow `handleResume` uses (open a scoped picker, then tag), or disable/hide the "Upload to Private Recordings" action inside the History disclosure and leave only "Fix the names and retry", which correctly resets to the idle picker. At minimum, guard `retryAsPrivateCollection` with `if (pendingFiles.length === 0) return;` plus a live-region message, so the flow never dead-ends silently.

## F5.14 [major] Every async store call is fired as `void p.then(...)` with no catch, producing unhandled rejections and silent dead-ends

File: /var/home/glw907/Projects/dubplate/web/src/App.svelte:153

Four sites launch a rethrowing store method with no rejection handler:

- App.svelte:93 — `void uploadStore.loadConfig().then(...)` (see the blank-page blocker).
- App.svelte:153 — `void uploadStore.createSession(album, collection, n).then(...)`. `createSession` rethrows on anything but a 401. A 429 from `maxSessionsPerUser`, or a plain network failure, leaves `phase === 'uploading'` with every row stuck at "waiting" forever and no `startFile` ever called. Nothing tells the user, and nothing recovers.
- History.svelte:36 — `void store.loadHistory()`. A failure renders "Nothing here yet.", actively lying about the user's uploads.
- History.svelte:131 — `onTryAgain: () => void retryProbe(row)`. `retryProbe` awaits `finishSession` then `loadHistory`; either can reject, so "Try again" silently does nothing.

In a browser these surface as `unhandledrejection` console noise only; the user sees a frozen UI.

Proposed fix: Give each an explicit `.catch` that sets a rendered error state. For `createSession` in particular, set `phase` back to a recoverable state and surface the reason — a 429 for the session cap is an expected, actionable condition the copy contract should cover, not an unhandled rejection.


## Standing mandate: idiomatic Svelte 5 / DaisyUI 5 (Geoff, 2026-09-01)

Push hard toward idiomatic Svelte 5 and DaisyUI 5 while folding, and treat
un-idiomatic code you touch as in scope:

- DaisyUI first: reach for the component class and its documented modifiers
  (alert, badge, steps, btn sizes, card, list) before hand-rolled utility
  stacks. Never fight a component's own layout model (the .alert grid
  finding is the canonical example). Colors come from theme tokens, never
  hardcoded values.
- Svelte 5 runes idiom: $derived for derived values (never an $effect that
  mirrors state), $effect only for real side effects with cleanup returned,
  $props() destructuring with typed defaults, callback props over
  createEventDispatcher, snippets over slots.
- If the idiomatic shape and a finding's proposed fix conflict, the
  idiomatic shape wins; note the divergence in your return.
