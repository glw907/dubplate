# Adversarial spec review: magic-link login + streamer SSO

Spec: `/var/home/glw907/Projects/dubplate/docs/superpowers/specs/2026-09-02-magic-link-login-design.md`

---

## Blockers

**[blocker] The `/rest/*` and `/share/*` bypass forwards client-supplied identity headers, which is total account takeover**
Spec:46-50 says those paths "pass through to the streamer completely untouched: no session check, no identity header." Spec:135-136 says stripping happens "on every request before its own evaluation" — which reads as stripping before *serve's* auth decision, not before *forwarding*. Under the untouched reading, `curl -H 'Remote-User: Geoff Wright' https://music.907.life/rest/...` arrives at Navidrome from the trusted source range with an attacker-chosen identity; Navidrome's reverse-proxy auth trusts the header whenever the peer is whitelisted, and it auto-creates users (spec:121-123), so this also mints arbitrary accounts. The strip must be unconditional on every proxied path including both bypass prefixes, and it must be worded as "strip on ingress, inject only on the session-gated path."

**[blocker] `ND_EXTAUTH_TRUSTEDSOURCES` pinned to "the compose gateway CIDR" trusts every container on the bridge, not just serve**
Spec:64-66. `compose.yaml:113-114` pins `subnet: 172.30.0.0/24`, `gateway: 172.30.0.1`. Serve reaches Navidrome through the loopback-published port (`compose.yaml:57-58`), so Navidrome sees the source as the gateway `172.30.0.1` — the whitelist must be `172.30.0.1/32`, never `172.30.0.0/24`, because the /24 also covers the `cloudflared` container. Combined with the next finding that is a remote, unauthenticated takeover; on its own it means any current or future container on `musicbox_default` can assert any user.

**[blocker] The live tunnel ingress rule routes `music.907.life` straight to Navidrome, bypassing the SSO proxy entirely**
`config/cloudflared-tunnel-config.json:10-13` sends the bare hostname to `http://navidrome:4533`. The spec's topology (spec:39-42) assumes serve is the ingress for the whole host, but nothing in the spec's build order (spec:176) says *delete* that rule, and cloudflared forwards arbitrary client headers. With a /24 whitelist, an internet request carrying `Remote-User:` reaches Navidrome from the cloudflared container's in-range IP and authenticates as any user. The spec must name the ingress rewrite (both rules collapse to `host.docker.internal:<port>`) as a precondition of turning ExtAuth on, not a step that happens to sit in the same task.

**[blocker] `/api/*` collides head-on with Navidrome's own web API, and the spec contradicts itself about it**
Spec:51-52 assigns "`/api/*` (dubplate's own API)" to dubplate, session-gated. Spec:62-63 then says "Navidrome's `/api/events`" streams through the proxy. Both cannot be true: Navidrome's SPA drives its whole native API under `/api/`, so rule 2 as written breaks the player, and the obvious repair — "proxy `/api/*` paths dubplate's mux does not match" — makes the auth boundary a function of mux-miss, so adding or renaming a dubplate route silently changes which side authenticates a path. Fix by moving dubplate's API under the `/upload` prefix it already owns (`internal/serve/serve.go:80`, `mountBasePath`), giving dubplate exactly one owned prefix and the streamer everything else.

**[blocker] The rate-limit key "per source address" is a single constant behind the tunnel, and the enumeration answer is explicitly resting on it**
Spec:136-140 and spec:85-87 ("The rate limits below bound what enumeration could probe"). Serve binds the bridge gateway (`compose.yaml:80-96`, `internal/serve/serve.go` `freebindListeners`), so every request's `r.RemoteAddr` is the cloudflared container's IP. A per-`RemoteAddr` limit is therefore global: five link requests per hour for the entire family, and one attacker's probing locks out every real member — while giving the attacker no isolation at all. The limit must key on `CF-Connecting-IP` (or a configured trusted-proxy header, with `RemoteAddr` fallback and a config flag for adopters with no proxy), and the spec must state that the header is only honored when the peer is the configured trusted proxy, or it becomes a trivially spoofed limit key.

**[blocker] Consumption on GET (implied) gives email-scanner prefetch, token-in-logs, and login CSRF**
Spec:94-96 says "Consuming the link sets the session cookie and redirects" — a link in an email is a GET, and nothing in the spec separates rendering from consuming. Three failure modes: an enterprise or provider scanner prefetches and burns the link (the family member's click fails, and worse, the scanner holds the session); the token rides the URL into cloudflared logs, Cloudflare's request logs, and browser history, contradicting spec:141-142 "tokens never logged"; and an attacker can force a victim's browser to a *link the attacker requested for themselves* via `<img>`/redirect, silently logging the victim into the attacker's identity, so the victim's uploads land in the attacker's inbox directory and ledger attribution. The spec must specify: GET renders an interstitial with the token in a hidden form field and `Cache-Control: no-store`, POST consumes it, and the POST is origin-checked.

## Major

**[major] Path normalization can smuggle a non-bypass path through the bypass prefix**
Spec:44-60 describes prefix routing with no statement about how the prefix is matched. Go decodes `%2F` into `r.URL.Path`, so `/rest%2F..%2Fapi/album` has `Path == "/rest/../api/album"`, which passes a naive `strings.HasPrefix(path, "/rest/")` bypass check; `httputil.ReverseProxy` then forwards the *raw* path and the streamer's own router cleans it to `/api/album`. The spec needs an explicit rule: reject any request whose `RawPath` differs from `Path` after cleaning, or route on `path.Clean` of the decoded path and forward the cleaned form, plus reject `..` segments, empty segments, and backslashes outright. `internal/serve/serve.go:88-94` already documents this exact class of gap for `mountBasePath`, so the precedent exists in-repo.

**[major] The existing CSRF check sits inside the `/upload` mount and will not cover any new surface**
`internal/serve/serve.go:254`: `securityHeaders(mountBasePath(requireSameOrigin(mux)))` — `requireSameOrigin` (`internal/serve/serve.go:152-176`) only sees requests already stripped of the `/upload` prefix. The login POST, the consumption POST, logout, and every proxied streamer mutation live outside that mount and would inherit no origin check at all. The spec never mentions repositioning it. `SameSite=Lax` is not a substitute (spec:102) — it is a bypassable default in some embedded webviews and does nothing for same-site-but-different-host attackers, which matters here because other `907.life` hosts exist.

**[major] `ReverseProxy` header hygiene is unspecified, and the default `Director` path is actively wrong**
Spec:62 names `httputil.ReverseProxy` with no rules. Two concrete defects follow from the default: `Director` + `X-Forwarded-For` *appends* to whatever the client sent, so a downstream that reads the first XFF entry sees an attacker-chosen IP; and hop-by-hop removal runs after `Director`, so a client sending `Connection: Remote-User` causes the freshly injected identity header to be deleted before it leaves (a downgrade/DoS on any victim the attacker can get to issue that request). Specify `Rewrite` with `ProxyRequest.SetXForwarded()` (which overwrites XFF and runs after hop-by-hop removal), inject the identity header inside `Rewrite`, and delete `X-Real-IP`, `Forwarded`, and `X-Forwarded-User`/`X-Forwarded-Host` on ingress.

**[major] Header spellings to strip are not enumerated, and the underscore class is the one that bites adopters**
Spec:135-136 says "any inbound trusted-header spelling." Go's `Header.Del` canonicalizes and removes duplicates for the exact dashed name, but `Remote_User` canonicalizes to `Remote_user` — a *different* key that Go does not fold, and that nginx/Apache/CGI front ends *do* fold into `Remote-User`. The spec should list the strip set explicitly and require it be driven by the driver's configured header name plus a fixed extras list: the configured name, its underscore variant, `Remote-User`, `Remote_User`, `X-Remote-User`, `X-Forwarded-User`, `X-Authenticated-User`, `X-WebAuth-User`, `X-Auth-Request-User`, `X-Auth-Request-Email`, plus `Cf-Access-Jwt-Assertion` (`internal/serve/serve.go:303`) once Access is no longer the source of truth. Strip must happen once, on ingress, before routing, for every path — not per-route.

**[major] The magic link's hostname source is unspecified — Host-header poisoning is the default failure**
Spec:88-89 says the link is HMAC-signed but never says where the link's scheme+host come from. If it is derived from `r.Host` or `X-Forwarded-Host`, an attacker POSTs `/login` with `Host: evil.example` and the family member receives a genuinely-signed token pointed at the attacker's server. The spec's own universality rule (spec:24-26, "No hostname... outside `internal/config`") argues for a required `DUBPLATE_PUBLIC_URL`, but the security requirements section (spec:135-146) must state it as a requirement and require that serve refuse to start without it once the login capability is enabled.

**[major] Session design has no absolute lifetime, no revocation, and no offboarding path**
Spec:100-106: 90 days, rolling refresh past halfway, revocation only by rotating the secret. A cookie stolen once renews forever, since every use past day 45 mints a fresh 90 days — there is no absolute cap. Worse for the estate: removing someone from `config/contributors.yaml` kills their dubplate access (the roster is checked per request, `internal/config/contributors.go:93`) but does **not** kill their streamer access, because spec:128-131 has every member self-set a Navidrome app password and spec:46-50 bypasses `/rest/*` entirely. Offboarding therefore requires a manual Navidrome admin step that the spec never names; add an absolute max lifetime, a cheap per-email "valid-after" epoch in the state dir, and an explicit deprovision runbook step.

**[major] The two HMAC secrets need domain separation, a minimum length, and a rotation overlap**
Spec:88, spec:100, spec:151-152 introduce `DUBPLATE_MAGIC_LINK_SECRET` and `DUBPLATE_SESSION_SECRET` with no stated construction. Three requirements are missing: a length floor enforced at config load (≥32 bytes; an adopter will otherwise paste a word), a purpose label inside the MAC input (`"dubplate/magic-link/v1"` vs `"dubplate/session/v1"`) so a token from one context can never verify in the other if the two secrets are ever set identically, and a documented rotation shape. As written, rotation is a hard cutover — spec:104 accepts signing everyone out, but a `SECRET`/`SECRET_PREVIOUS` accept-old-verify-new pair costs nothing and makes rotation routine rather than a scheduled outage. Also specify the token's serialization is unambiguous (length-prefixed or JSON), since an email containing the field delimiter otherwise allows claim confusion.

**[major] The nonce set is memory-only and restarts are more frequent than the spec assumes**
Spec:89-93 accepts a replay window across a restart. The acceptance under-weights how a restart happens: `scripts/deploy.sh` restarts the unit on every deploy, and systemd restarts on OOM — and a large tus upload is exactly the OOM trigger. That makes the window attacker-*influenceable*, not merely incidental. The fix is cheap enough that the tradeoff should not be taken: append consumed nonces to a file in the state dir with TTL pruning, the same durability the ledger already has. Also specify the ordering explicitly — verify MAC, then check expiry, then insert the nonce — so an attacker cannot grow the set with unverified input.

**[major] Unauthenticated input reaches unbounded in-memory maps**
Spec:136-140 puts a per-email rate limiter in front of an endpoint that any internet client can now POST. Nothing bounds the submitted email's length or the number of distinct keys, so an attacker walks a million distinct addresses and the limiter map is the memory-exhaustion primitive. Requirements the spec should carry: `http.MaxBytesReader` on every auth endpoint body (`internal/serve/upload.go:1030` already does this for session creation — same pattern), a hard email-length cap, `net/mail.ParseAddress` validation, and a bounded/evicting limiter structure. Related: normalize the email to lowercase *before* keying the limiter, or `Geoff@` and `geoff@` are separate buckets and the per-email cap is trivially multiplied into a mail-bomb (`internal/config/contributors.go:93` lowercases for roster lookup; the limiter must match).

**[major] "SSE stream correctly through it without extra configuration" is false against the current server config**
Spec:62-64. `internal/serve/serve.go:599-604` sets `WriteTimeout: 30s` and `ReadTimeout: 30s` process-wide; `clearBodyDeadlines` (`internal/serve/upload.go:322-335`) lifts them only for the tus route. Every SSE connection and every audio stream through the new proxy gets cut at 30 seconds. Not a security bug, but it is a load-bearing design claim that is wrong, and the repair (per-route deadline clearing on the proxy path) has security-adjacent consequences worth specifying: an unbounded-duration proxied route is also a slow-loris surface now that the endpoint is anonymous-reachable.

**[major] The session cookie is forwarded to the streamer and has no `__Host-` prefix**
Spec:100-102 lists `Secure`, `HttpOnly`, `SameSite=Lax` and no name prefix. Two gaps: `ReverseProxy` forwards the `Cookie` header verbatim, so dubplate's session token lands in Navidrome's request handling and any request logging it does — strip the session cookie before proxying. And without `__Host-`, any other host under `907.life` (or anything that can set a `Domain=.907.life` cookie) can shadow the session cookie, which is at minimum a persistent DoS and at worst a fixation aid. `__Host-` also forces `Path=/` and `Secure`, both of which this design wants anyway.

**[major] The identity header value is the roster `name`, with no uniqueness or charset constraint**
Spec:118-120. `internal/config/contributors.go:50-56` builds `byName` from free-text YAML with no validation: two contributors sharing a name silently collapse to one streamer account (identity confusion, cross-user library and playlist access), and a name containing CR/LF or non-ASCII either fails the outbound request (Go rejects invalid header values — a hard DoS for that member) or, behind a laxer proxy, injects. Require at roster load: unique names, ASCII-printable, no control characters, bounded length — and say plainly that the header value must be a stable unique identifier, not a display name.

**[major] Dual auth paths must be mutually exclusive**
Spec:110-114 retires `internal/access` "from the family path" while keeping the seam "so any forward-auth front (Access included) can layer back in front," and spec:155-158 drops the Access config from the required wall. If the code still consults `Cf-Access-Jwt-Assertion` when the header is present but the team domain and AUD are empty, you have two identity sources with one of them unconfigured. `internal/access/access.go:85-92` builds `certsURL` as `"https://" + teamDomain + certsPath` — with an empty domain that is `https:///cdn-cgi/access/certs`, which fails closed today, but the spec should state the invariant rather than rely on it: exactly one identity source is active per deployment, selected by config, and the inactive one is not consulted at all.

## Minor

**[minor] Redirect validation needs its bypass list spelled out**
Spec:95-96 says "validated as same-origin relative, never an absolute URL." The classic bypasses all satisfy a naive "starts with `/`" test: `//evil.example`, `/\evil.example`, `/\/evil.example`, `\/\/evil.example`, `https:/evil.example`, and percent-encoded variants (`%2f%2fevil.example`) if the value is decoded twice. State the positive rule instead: accept only a value matching `^/[^/\\]` after a single decode, reject anything containing a scheme, `..`, or a control character, and re-validate after decoding rather than before.

**[minor] The kindness-over-enumeration choice has a second-order cost the spec does not price**
Spec:79-87 accepts telling a visitor whether their address is on the roster, bounded by rate limits. Two things the record should add: the mitigation it leans on is broken (see the rate-limit blocker), and the login page also publishes the admin's contact address (spec:83-84), so the pair hands a phisher a confirmed recipient list plus the authority address to spoof — on an estate whose whole roster is a handful of relatives. A same-response-both-branches design costs one sentence of copy ("If that address is on the list, a link is on its way"), and the "mistyped email deserves an answer" goal survives it.

**[minor] Differential auth errors are half-invited by the API-contract requirement**
Spec:143-144 requires machine-readable errors "consistent with the API contract." That contract's existing shapes (`internal/serve/serve.go:329-342`) distinguish `unauthenticated` from `not_on_roster` — reasonable post-auth, dangerous on the consumption endpoint, where "expired" vs "already used" vs "bad signature" tells an attacker whether a token they hold was real. Require one generic outcome for every consumption failure, with the distinction recorded only in server logs.

**[minor] Security headers and edge caching for proxied responses are unspecified**
`internal/serve/serve.go:119-128` applies a tight `default-src 'self'` CSP to everything it wraps. Applied to the proxied Navidrome SPA it will likely break the player (blob/data media sources, inline styles); excluded, the player ships with no `nosniff`, no frame denial, no CSP. Decide it per surface in the spec. Same section should say that proxied, identity-injected responses carry `Cache-Control: private` and `Vary: Cookie`, and that the Cloudflare cache is configured to bypass the host — a per-user response cached at the edge under a shared URL is a cross-member data leak.

**[minor] `Referrer-Policy` and third-party resources on the auth pages**
`internal/serve/serve.go:123` sets `no-referrer` globally today; the spec (spec:74-78) says the login page shares the uploader's compiled CSS and carries no JavaScript, which is the right shape. Record it as a requirement rather than an inherited accident: the login and consumption pages load no third-party origin, and `no-referrer` applies to them — otherwise a token-bearing URL leaks via `Referer` if consumption stays on GET.

**[minor] `ND_EXTAUTH_TRUSTEDSOURCES` may not be the setting name for the pinned version**
Spec:64-66 names it; `compose.yaml:27` pins `deluan/navidrome:0.63.2`. The reverse-proxy auth pair I can account for in the 0.6x line is `ND_REVERSEPROXYUSERHEADER` / `ND_REVERSEPROXYWHITELIST`. A mistyped setting name is silently ignored by Navidrome, which here means SSO quietly does not engage and members hit the streamer's own login page — or, if the intended fail-closed behavior differs from the actual one, worse. Verify against the pinned version's docs and add a bring-up assertion that proves injection works *and* proves a spoofed header from a non-whitelisted source is rejected.

**[minor] SMTP construction from roster values needs explicit CRLF rejection**
Spec:81-83 sends to the roster-matched address. The address is admin-authored YAML (`internal/config/contributors.go:14-17`) with no validation, so a `To:` built by string concatenation from a value containing `\r\n` injects headers (Bcc, Reply-To) into the outgoing message. Low likelihood, one-line fix: parse every address with `net/mail.ParseAddress` at roster load and fail the config, not the send.

**[minor] The login page must escape the submitted address if it echoes it**
Spec:82-84 describes a friendly "not on the list" response. If the page renders the submitted email back, use `html/template` — a `text/template` or `fmt.Appendf` render is stored-nothing but reflected XSS on the one unauthenticated, pre-session page in the estate. `warmRosterAbsentPage` (`internal/serve/serve.go:347-360`) currently builds HTML with `fmt.Appendf` over a config value, which is safe only because that value is trusted; a user-supplied value must not follow the same pattern.

**[minor] "First user becomes admin" is documentation, not a control**
Spec:121-125 notes the estate's admin predates the change and the runbook documents the ordering for fresh adopters. For an adopter, whichever roster member logs in first silently becomes the streamer admin. Worth stating a mitigation in the runbook: create the admin account before enabling the SSO capability, and have bring-up verify the admin exists.

**[minor] What Access retirement removes, beyond rate limiting**
The spec (spec:136-140) treats rate limiting as the replacement for edge auth. What Access also provided: no anonymous request ever reached the box, so the Go HTTP stack, tusd, and every dependency were not internet-attackable, and there was no anonymous DoS surface. Additional requirements worth naming: keep serve bound to the bridge gateway and loopback only (`compose.yaml:80-96` — never `0.0.0.0`), confirm no host firewall rule exposes the serve port, add body caps and bounded limiters (above), log every auth event (link requested, link consumed, consumption failure, rate-limit trip, header-strip hit) with the real client IP since that is now the only audit trail, and keep a Cloudflare WAF rule or Turnstile available as the fallback for the login endpoint. Also record that `/rest/*` is now an unauthenticated, unrate-limited password-guessing surface against Navidrome accounts whose passwords are stored recoverably (`compose.yaml:41`, `ND_PASSWORDENCRYPTIONKEY`).

**[minor] `SameSite=Lax` is right for the tus surface, wrong to rely on alone**
Spec:102 with the tus endpoints: tus-js-client sends `Tus-Resumable`, so PATCH/POST are preflighted and same-origin, and Lax breaks nothing. The residual is that Lax still sends the cookie on cross-site top-level GET navigations, which is exactly when serve would inject the identity header into a proxied GET — any GET-triggered state change in the streamer is then CSRF-able. Keep Lax (Strict would break the magic-link landing), but the origin check must cover the proxy path, and the spec should say the proxy refuses to inject on any non-idempotent method lacking a same-origin signal.

**[minor] Rolling refresh has no stated trigger boundary**
Spec:101-102 refreshes "on use past the halfway mark." Say which requests count: if any proxied GET refreshes, a cross-site top-level navigation (Lax) refreshes an otherwise-idle session indefinitely without the user ever interacting with the site. Refresh on same-origin requests only, and cap by the absolute lifetime above.

## The three I would fix first

1. **The proxy trust boundary as one unit** — unconditional identity-header strip on ingress for *every* path including `/rest/*` and `/share/*`, `ND_..._TRUSTEDSOURCES` narrowed to `172.30.0.1/32`, and `config/cloudflared-tunnel-config.json:10-13` repointed at serve. These three are one attack: any of them left as written is remote, unauthenticated account takeover.
2. **Split link consumption into GET-renders / POST-consumes**, with the token in a form body, `no-store`, an origin check, and durable nonce storage. This closes scanner prefetch, token-in-logs, and login CSRF together, and it makes spec:141-142's "tokens never logged" actually true.
3. **Fix the rate-limit key and the `/api/*` collision** — `CF-Connecting-IP` gated on a configured trusted proxy, and dubplate's API moved under the `/upload` prefix it already owns. The first is the mitigation the spec's enumeration tradeoff is explicitly resting on; the second decides the auth boundary by configuration instead of by mux-miss.

**Verdict: not ready to build — six blockers, of which the header-strip/trusted-source/tunnel-ingress trio is remote unauthenticated account takeover as currently worded.**
