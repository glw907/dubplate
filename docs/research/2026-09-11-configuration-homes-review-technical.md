# Adversarial review: `2026-09-11-configuration-homes-design.md`

## (a) Defects that must change the spec

**A1. Hardlink copy-on-write is safe only if *every* writer in the estate is the atomic writer — and today's estate has one that is not: beets.** The spec's whole CoW argument is "every tag write goes through the atomic writer, so the rename splits the inode." beets/mutagen rewrite tags **in place** (open, seek, write), and rung 16's migration and the current box run beets. `metaflac`, `ffmpeg -i … file.flac` variants, `rsync --inplace`, and any member's tag editor on a laptop-written mirror do the same. Failure: member A retags one track in collection A; the file has `st_nlink == 2`; collection B's supposedly-independent album silently changes tags, and B's owner's per-collection tagging policy is now violated with no event anywhere. Fix: state the invariant as an enforced rule, not a convention — before any write to a library path, `stat` it and if `st_nlink > 1` break the link by copy-then-atomic-rename (a `breaklink` helper in the engine); forbid beets from ever writing tags to a hardlinked tree (rung 16 migration must land into a single-link tree and share inodes only afterwards); add a doctor check that reports library files with `st_nlink > 1` whose collection rows disagree on tags. Also prefer `FICLONE` reflinks where the filesystem offers them and say *why*: with a reflink an in-place write by a foreign tool damages only that copy. Hardlinks make the foreign-writer hazard estate-wide; reflinks do not. That is not a cosmetic difference and the spec presents them as equivalent.

**A2. Hook 1 conflates two different hashes, and the "computed at rung 7's gate on the uploaded bytes" phrasing is genuinely in conflict.** The decoded-audio MD5 is (i) not computed from the uploaded bytes — it is *read* from STREAMINFO, or else obtained by a full decode; and (ii) invariant under retag, which is exactly what the drift check and the transcode-cache invalidation need it *not* to be. The 2.0 spec says cache invalidation "is a delete on retag" and that the drift walk re-hashes "a hash that no longer matches" — neither works with an audio MD5. Fix: name two columns. `audio_key` (FLAC decoded MD5; identity, dedupe, overlap report, cross-collection sameness) and `file_hash` (BLAKE3/SHA-256 over the file bytes, computed streaming at the rung 7 gate; drift detection, cache key, backup change detection). Update hook 1 and the transcode-cache decision accordingly.

**A3. A zero/absent STREAMINFO MD5 is common, and the spec has no fallback.** GStreamer's `flacenc` (Sound Juicer), Qobuz downloads, and `flac --no-md5-sum` all ship all-zero MD5 fields; `flac -t` warns "cannot check MD5 signature since it was unset". Failure: two members upload different albums from Qobuz; both carry MD5 = 0…0; the overlap report calls them the same audio and the second upload is refused as a duplicate. Fix: treat all-zero as *absent*, never as a value; on absence compute the MD5 by decoding at the rung 7 gate (one decode of the uploaded album, bounded and already paying for verdict work) and record `audio_key_source ∈ {header, computed}`. Add the rule that the header value is *untrusted metadata* — it is whatever some encoder wrote — so the gate verifies by decode at admit for uploaded content, or the spec must say plainly that identity is "what the encoder claimed" and accept forgeable/wrong keys.

**A4. Identical PCM across genuinely different releases is normal, so the audio MD5 must never be an identity by itself above track level.** A track on a single and on its album, a bonus track repeated across editions, and above all short silence/HTOA tracks collide exactly. Failure: "refusing a re-upload" rejects a legitimate album because three of its tracks matched existing inodes; the duplicate-collapse view merges a single into an album. Fix: album-level sameness is the multiset of track `audio_key`s **plus track count and ordering**, never a per-track match; re-upload refusal is album-keyed; and hardlink sharing (a storage optimization) must stay decoupled from identity (a catalog judgment), which the spec half-says and then violates in the "refusing a re-upload" sentence.

**A5. Settings that are consumed by a *different unit* cannot live in the store as stated.** "Backup schedule" is `dubplate-backup.timer`, a systemd unit; the store cannot change it. "Monitoring ping URLs" are read by `dubplate-ping-fail@.service`, a separate unit with its own env. Failure: an admin sets a nightly backup time in the 2.0 admin page, the page confirms, the timer still fires at the old hour, forever, with no error. Fix: split each row by *consuming process*. Backup **targets** → store (the `dubplate backup` process is the same binary and can read it). Backup **schedule** → stays env/unit, or the server owns an internal scheduler and the timer is deleted. Ping URLs consumed by `ping-fail@` → env until that unit reads the store. Add a required column to the home table: which process reads this key.

**A6. Env-as-first-boot-seed is a silent-drift machine, and it contradicts the wall's own compat discipline.** `config.Load` makes an unknown key a *load error* precisely so nothing degrades silently; then this spec makes a *known* key silently ignored after first boot. Failure: SMTP host rotates, the age store and `deploy.sh` render the new value, the unit restarts, mail keeps going to the dead host; `doctor` says everything is set. Fix: record on each settings row `seed_value`, `source ∈ {default, env-seed, admin}`, actor and timestamp. At boot, for each store-homed key present in env: if the row is still `env-seed` and env differs from `seed_value`, re-seed (env wins, logged); if the row is `admin`, **fail the load** naming both values and the API that would resolve it. That preserves the wall's loud-failure property and keeps `deploy.sh` working unchanged.

**A7. The group-total quota must not be charged the per-collection way.** Charging every referencing collection full `st_size` is right for *liability* (and matches backup cost — see B2 — so it is a good choice). But the spec says all three levels work that way, and the group total exists "because the box has one disk". Failure: three collections share one inode set; the group total reads 3× physical; the admin is told the disk is full while `df` shows half free, and intake stops. Fix: group total is measured physically (inode-deduped `du` over the library root, or `df` on the library filesystem), per-member and per-collection stay charged-per-reference, and the spec names them as two different numbers with two different names.

**A8. `owner` nullable-meaning-the-admin is a magic value.** NULL has to be interpreted, the interpretation moves when the admin account changes, and it fights hook 5's durable surrogate id. Fix: `owner` is NOT NULL referencing the surrogate user id; member removal *tombstones* the user row (`removed_at`) rather than deleting it, so playlists, history, starred and collections keep referential integrity and the audit trail survives; only preference rows are deleted; transferred playlists get an explicit owner rewrite with a name-collision rule. Related and checkable: SQLite enforces foreign keys only with `PRAGMA foreign_keys=ON` **per connection** — with modernc and a pool that must be in the DSN, or every FK rule in this spec is decorative.

**A9. Move must be link-then-unlink with a durable intent journal; "one transaction" is not available.** The filesystem is not in the DB transaction. Failure modes the spec leaves open: crash after commit and before rename leaves rows pointing at nothing; a Navidrome scan landing mid-move sees tracks missing from library A and marks them missing (and on the next purge deletes its per-user rows for them). Fix, as an explicit ordering rule: write a `move_intent` row in the same transaction as the catalog change; then for each file create the target entry (rename within one filesystem, else link+unlink), fsync the directories, then remove the source entry; replay the journal at startup; suppress scan triggers for the duration and fire exactly one scan after. Never unlink before the target entry exists.

**A10. The "no API for per-user library access" justification for 1.0 is probably false and should not be a load-bearing sentence.** Navidrome has multi-library with per-user grants since 0.58 (0.63.2 is well past it), administered through the native REST API that already drives its own web UI — the same unstable native API the rung 12 driver must use for roster sync and SSO anyway. Fix: change the sentence to a rung 12 *verification task* against the pinned build, not an asserted capability gap. Two constraints come with it and belong in the spec: Navidrome libraries must be **non-overlapping root folders**, so a collection's layout template is relative to its own subtree root, and library ids are Navidrome-side state the driver must map and persist.

## (b) Risks the rung plans must carry as tasks

**B1. Navidrome PID collisions between hardlinked, identically tagged files in two libraries.** Default `PID.Track` is derived from tags, not inode or path; Navidrome's own tracker carries duplicate/missing-track bugs from exactly this shape (issues #3953, #4176, PR #5183). The realistic outcome is that the "same album in two collections, visible by design" case renders as one album, or flaps between libraries per scan. Rung 12 task: reproduce against 0.63.2 with two libraries holding hardlinked copies, record the behavior, and pin a `PID.Track`/`PID.Album` formula that includes the library or path if one exists.

**B2. Backup does not preserve hardlinks and restore does not rebuild them.** rclone transfers hardlinked files as independent objects (open feature request #6160), and R2 has no link concept at all. Consequences to write down: backup bytes and R2 cost equal the *charged* quota number, not the physical one; after a restore the library is strictly larger than the box it came from and may not fit; and the restored tree has every link broken, which is *safe* but changes disk math. Rung plan tasks: state the restore size expectation in the runbook, and add an optional post-restore relink pass keyed on `audio_key` + byte equality.

**B3. Cross-device staging.** `os.Rename` fails with `EXDEV`. Today `/srv/music/uploads` and `/srv/music/library` are the same volume and `/var/lib/musicbox` is not — that is luck, not a rule. Task: a doctor/gate check that the tus staging dir, the library root, and every collection subtree share one `st_dev`, with a copy fallback (never a hard failure) and an explicit error when a hardlink across collections is impossible.

**B4. Sweep-versus-writer races.** The link-count sweep must not delete a file whose row is committed but whose filesystem work is in flight (intake, move replay, mirror push). Task: the sweep only considers paths with no open intent-journal row and older than a grace interval, takes the same per-collection lock the writer takes, and is dry-run-first.

**B5. Reload semantics per key.** Give every store-homed key an `applies ∈ {immediately, next operation, restart}` field, surface it in the admin API and in `doctor`, and forbid long-lived cached config: consumers read through an accessor with a version-counter invalidation (single process, so this is cheap). Session/token lifetime changes need a stated rule for already-issued tokens. Driver choice and URL are `restart` in practice — say so rather than listing them as "live".

**B6. Writer identity is undefined.** "A named binary instance" never says how a laptop is named. Task, for the TUI initiative and the rung 14 API: the writer id is a server-minted opaque id **per profile, not per machine** (two profiles on one laptop = two writers), with a secret token stored `0600` under `$XDG_STATE_HOME/dubplate/` (settings themselves under `$XDG_CONFIG_HOME`, local profile store under `$XDG_DATA_HOME`), never derived from hostname or MAC. Seize revokes the token. A reinstalled laptop re-registers as a *new* writer and needs an explicit admin "adopt" action, or the mirror is orphaned. Crucially, add a monotonic **writer epoch** bumped at every registration: a restored laptop image running the same token concurrently with the original is otherwise undetectable, and "exactly one writer" is then a hope rather than an invariant.

**B7. Mirror quota enforcement.** The server gates intake per album but not mirror pushes. Task: a mirror push declares its total byte count up front and takes a *reservation* against member and group quotas before any bytes move, with a true-up at completion and a defined partial-mirror state; concurrent uploads must reserve too, or two uploads each passing the check overshoot.

**B8. Optimistic concurrency on collection rows.** Last-write-wins is fine for scalar settings, not for a layout template whose write triggers a re-lay of files. Task: `if_version` on collection-shape edits, and re-layout serialized as one job per collection.

**B9. Default-collection resolution must re-check at write.** Resolving only at page load leaves a window; the write must re-validate and return a typed error rather than silently falling back, which is the exact failure the paragraph says is worst.

**B10. Local store years behind.** goose replays forward fine; the untested direction is a *newer* laptop store talking to an older server. Task: version negotiation on connect with a refuse-and-explain rule, and a statement that mirror/hand-over pushes are versioned row-level API calls, never a schema-shaped dump. Also soften "one schema": per-member overrides and preference tables are meaningless locally, so it is one *settings* schema with a server-only extension, and the spec should say which tables are shared.

**B11. Retire under the Navidrome driver.** Un-projecting a collection removes a Navidrome library, and Navidrome will mark its tracks missing and eventually purge them along with its per-user stars and playlist entries. At 1.0 those are Navidrome's only home. Task: record this loss in the retire confirmation copy, or block retire until 2.0.

**B12. 2.0 projector enforcement surface.** For per-user music folders: `getMusicFolders` returns only permitted libraries; a repeatable `musicFolderId` accepted on `getAlbumList2`, `getArtists`, `getIndexes`, `search3`, `getStarred2`, `getRandomSongs`, `getGenres`, `getTopSongs`; playlists and starred filtered per item at read; `stream`, `download` and `getCoverArt` authorized by item rather than by possession of an id; and share links re-checked at fetch time so revoking visibility breaks a live share. Worth a conformance test list in the rung plan, not prose.

## (c) Fine, and why

- **Charging every referencing collection full size.** Over-counts, but it matches backup and restore bytes exactly (B2), removes gaming, and is explainable. Keep it — just not for the group total (A7).
- **Copy as a row-level snapshot, reference declined.** Correct: one writer per row is the only invariant that makes mirroring tractable, and a shared row would break per-collection tagging policy.
- **Move minting a new album id, with the loss named by count in the confirmation.** Honest and cheap; re-pointing per-member rows really would break the identity rule.
- **Visibility landing on the row at rung 6 while the feature waits for 2.0.** A reader axis retrofitted after collections exist is a projector rewrite; the column costs nothing now. The "never confidentiality from the admin" sentence is the right thing to write down.
- **Per-member objects keyed to the member with visibility computed at read time**, rather than Jellyfin's playlists-as-a-library. This is the correct model and the reason B12's per-item filtering is tractable.
- **One roster, one identity kind, one admin flag**, with capability differences as per-member overrides. Declining account classes avoids the permission-matrix explosion that produces Jellyfin's "cannot open my own playlist" bug.
- **Machine settings never sent to the server**, and profiles switching modes rather than merging local and server settings. This is what removes synchronization from the design, and it holds.
- **The atomic writer itself** (`internal/atomicfile`) is sound for this use: temp file in the destination directory, explicit chmod before rename, directory fsync in `WriteStream`. The CoW property really does fall out of it — the gap is A1, foreign writers, not this package.
