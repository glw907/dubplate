# Conformance corpus

This directory is the frozen fixture corpus rung 2 builds against: a
MusicBrainz response set captured once, pinned beets driven against it,
and the derived oracle record checked in alongside the fixtures. Nothing
here is regenerated by the gate; `internal/harness/cassette` only reads
and validates it.

## Layout

```
corpus/
  manifest.json          # pins the corpus's meaning; see below
  profiles/               # beets config profiles: estate.yaml, stock.yaml
  cases/
    <id>/
      case.json           # the case's metadata: input, request log, expected record
      responses/
        NNN.json           # a verbatim MusicBrainz response body
```

`case.json` decodes into `cassette.Case`. Its `requests` field is the
committed request log: an expectation the harness replays against, not
scaffolding to regenerate. A response body lives only as a file under
`responses/`; `case.json` never embeds one inline, so there is never a
decode-and-re-encode step that could disturb its bytes. `Case.Extra`
lists response files a case captured but no logged request currently
consumes: recall-extension fixtures for a future candidate-widening
improvement (U8), graded on the same shared subset rather than escaping
the harness.

`corpus/cases/` is empty as of this task; the smoke corpus lands in
pass 2a's Task 5, once the pass's MusicBrainz contact input is in hand.

## The canonicalization rule

A case's `requests[].path_query` is the request's path plus its raw
query string, stored in canonical form: **the query's `&`-joined
`key=value` pairs are sorted byte-wise, and nothing else changes.** The
rule never decodes and re-encodes a pair. Three facts about the wire
format would not survive that round trip:

1. **`fmt=json` is forced on every request.** beets' MusicBrainz client
   always adds it; a captured request that lacks it was not actually
   issued by pinned beets.
2. **`inc=` values join with a literal `+`.** `inc=artists+media` is one
   query parameter with a `+`-joined value list, not two parameters; a
   decode step that treats `+` as a space (the `application/
   x-www-form-urlencoded` convention) corrupts it.
3. **Search queries carry Lucene escapes.** beets' search fallback
   builds a Lucene query string with its own escaping (`\"`, `\+`, and
   so on) before URL-encoding it; decoding and re-encoding can silently
   change which characters are escaped.

`cassette.LoadCase` rejects a case whose stored `path_query` is not
already in this canonical form, so a case can never depend on a replay
lookup silently reordering pairs for it. The path portion, including
any trailing slash, is never touched by canonicalization: two requests
differing only by a trailing slash name different resources and stay
distinct, they do not collapse into the same canonical key.

## The manifest

`corpus/manifest.json` pins every version the corpus's derived
`Expected` records depend on: the beets version, its
`unidecode`/`jellyfish`/`lap`/`numpy` dependency versions, the shim's own
version, and a content hash per config profile. `cassette.LoadManifest`
parses the file and checks its shape only (a schema version and a beets
pin must be present); reconciling the dependency and profile pins
against a live venv is derivation-time work, done by the oracle
package's `Reconcile` when pass 2a's Task 3 lands. Until then, the
dependency and profile fields stay empty: they are not yet known,
not defaulted.

A profile edit, or a beets/dependency version bump, is a
corpus-revalidation event exactly like any other pin change: whatever
in the manifest disagrees with the new venv is what `Reconcile` names.

## Config profiles

`corpus/profiles/estate.yaml` derives from `config/beets-config.yaml`,
dubplate's live import profile, under the transform below: every
verdict-moving key survives verbatim, every key that only affects
importer execution or output layout is dropped, and the plugin set
narrows to the single metadata source the corpus's design requires
(ruling 3: multi-source ordering would break tie reproducibility). A
profile edit is a corpus-revalidation event exactly like a beets
version bump (`corpus/manifest.json`'s `profile_hashes` is what
detects it), so this table is the record a reviewer checks a profile
change against, not decoration.

| `config/beets-config.yaml` key | estate.yaml fate | reason |
| --- | --- | --- |
| `directory` | box path, replaced by the `{{DUBPLATE_LIBRARY_DIR}}` placeholder | never a corpus value; `internal/harness/oracle` substitutes a per-run scratch path at derivation time |
| `library` | box path, replaced by the `{{DUBPLATE_LIBRARY_DB}}` placeholder | same |
| `import.move` | dropped | import-execution behavior; the oracle runs no importer and moves no files |
| `import.write` | dropped | import-execution behavior; the oracle never writes a tag to disk |
| `import.quiet_fallback` | kept verbatim | the quiet-mode trio: verdict-moving (governs what a non-interactive run resolves an ambiguous match to) |
| `import.none_rec_action` | kept verbatim | quiet-mode trio |
| `import.timid` | kept verbatim | quiet-mode trio |
| `import.group_albums` | dropped | the corpus tests the matcher from the (items, responses) boundary, below the importer's own grouping step (mechanics study, "Item order and the group_albums pre-step") |
| `original_date` | kept verbatim | verdict-moving: controls which year the year penalty evaluates against |
| `per_disc_numbering` | kept verbatim | verdict-moving: affects multi-disc track distance and assignment |
| `paths.*` | dropped | output filename templates; the matcher never reads them |
| `plugins` | reduced to `musicbrainz` alone | the single-metadata-source constraint; `fetchart`, `embedart`, and `replaygain` are matching-inert per the mechanics study but import-active, so they cannot ride even reduced |
| `fetchart.*` | dropped | config for a plugin no longer loaded |
| `replaygain.*` | dropped | same |
| `embedart.*` | dropped | same |
| `match:*` | absent from both files, kept "verbatim" at beets' shipped defaults | `config/beets-config.yaml` sets no `match:` override, so estate.yaml runs the whole distance/threshold surface at beets' defaults too |
| `musicbrainz:*` | absent from the checked-in file; injected at derivation time | `config/beets-config.yaml` sets no `musicbrainz:` override either; the adapter appends `musicbrainz: {host: "<stub addr>", https: no, ratelimit: 100}` when it renders the profile, pointing the run at the running replay stub instead of the live API (the Q5 seam) |

`corpus/profiles/stock.yaml` is the defaults profile: `plugins:
musicbrainz` and nothing else, not even the box-path placeholders.
Every other surface, including `match:`, runs at whatever beets ships
as its own default. It exists for the same single-source reason as
estate's `plugins:` line, on a config that never overrode any of the
matcher's other knobs to begin with.

Both profiles are plain YAML text; `internal/harness/oracle` renders
one by substituting the `{{DUBPLATE_LIBRARY_DIR}}` /
`{{DUBPLATE_LIBRARY_DB}}` placeholders (a no-op on stock.yaml, which
carries neither), then appending the `musicbrainz:` stub-host block.
The adapter rejects a rendered profile whose `plugins:` line resolves
to anything other than exactly one recognized metadata-source plugin,
so a profile edit that reintroduces a second source, or drops
`musicbrainz` entirely, fails loudly at derivation time rather than
silently changing which source produced a case's `Expected` record.

## The capture tool

`cmd/harness` (`harness capture`) is the workstation dev tool that
populates a case's `responses/` directory from the live MusicBrainz
API. It is never shipped, and the repository gate never runs it
against the network: `go test` exercises only its request planning
and file I/O, against a fake fetcher.

Two verbs, matching the capture-derive loop's two halves:

- **`harness capture --mbid <release> --out corpus/cases/<id>`** seeds
  a case: it fetches the release lookup at beets' own maximal `inc=`
  (`RELEASE_INCLUDES`, mechanics study Q5) rather than the minimal set
  today's matcher happens to read, so a future matcher improvement
  that wants another field never forces a re-capture (U6). When the
  fetched release carries `status: "Pseudo-Release"` and a backward
  `transl-tracklisting` relation, it follows that relation and fetches
  the linked actual release too, at the same maximal `inc=` (Q5, item
  7): beets merges the two AlbumInfos internally, so a capture missing
  the second release would replay a 404 the moment pinned beets
  follows it. Both response bodies are written verbatim with
  `os.WriteFile`, never re-encoded. The seeded case carries only its
  request log; `Input`, `Profile`, and `EvalDate` are a human's job
  once a case is seeded, since none of them is derivable from an MBID
  alone.
- **`harness capture --case <dir>`** consumes an existing case's miss
  list: it fetches exactly the requests named in `<dir>/misses.json`
  (see "The miss-file mechanism" below), appends each as a logged
  `Request`, and removes the miss file once every fetch succeeds. A
  fetch failure leaves both the case and the miss file untouched, so a
  retry never loses partial progress.

**Wire discipline**, both verbs: at most one request per second within
a single invocation (the first request pays no wait; every request
after it does); every request carries the identified User-Agent
`dubplate-harness/<version> ( $DUBPLATE_HARNESS_CONTACT )`; the tool
refuses to run at all when `DUBPLATE_HARNESS_CONTACT` is unset or
empty, since MusicBrainz's terms require a reachable contact in every
request and this tool never substitutes a literal for it (CLAUDE.md's
universality rule).

### The miss-file mechanism

`internal/harness/oracle.Derive` starts a `stub.Server` over a case's
existing responses and runs pinned beets against it. When beets issues
a request the case log does not cover, the stub answers 404 and
records a `stub.Miss` (method plus canonical path+query). After the
shim process exits, `Derive` writes every miss it collected to
`<case dir>/misses.json` as a JSON array of `stub.Miss` values
(`{"method": "...", "path_query": "..."}`); when a derivation sees no
misses at all, `Derive` removes any stale file instead, so a case
directory's `misses.json` always reflects only its most recent
derivation. `harness capture --case <dir>` reads that same file and
`stub.Miss` shape directly (no separate schema to keep in sync), which
is what makes the file the load-bearing handoff between a derivation
and the next capture, rather than scaffolding a human has to
transcribe by hand.

### A recorded fixed point, not a stable request set

The capture-derive loop (capture, derive, capture the derivation's
misses, derive again) converges when a derivation records zero misses.
That convergence is a **fixed point of one specific pinned-beets run
against today's captured data**, not a promise that the request set
itself is stable or minimal. In particular, a strong ID-lookup match
retires beets' search fallback for that item: once a release lookup by
MBID scores a strong recommendation, beets never issues the search
request an earlier, less complete capture might have needed. Any
response already captured for that now-unreachable search request does
not become wrong; it becomes `Extra` (recall-extension surface, U8),
legally orphaned by a more complete capture rather than a regression
to fix. A case's `Extra` list is exactly where those orphaned
responses belong once a maintainer notices the loop has converged past
needing them.
