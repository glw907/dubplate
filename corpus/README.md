# Conformance corpus

This directory is the frozen fixture corpus rung 2 builds against: a
MusicBrainz response set captured once, pinned beets driven against it,
and the derived oracle record checked in alongside the fixtures. Nothing
here is regenerated by the gate; `internal/harness/cassette` only reads
and validates it.

## Layout

```
corpus/
  manifest.json          # pins the corpus's meaning; see below
  profiles/               # beets config profiles: estate.yaml, stock.yaml
  analysis/               # the corpus-wide analyses; see "The analyses"
    proximity.json
    ties.json
    components.json
    divergences.md
  cases/
    <id>/
      case.json           # the case's metadata: input, request log, expected record
      claims.json         # what the author claims the record shows
      responses/
        NNN.json           # a verbatim MusicBrainz response body
      misses.json           # transient; see below
```

`misses.json` is not part of a case's committed fixture: it is the
miss list `oracle.Derive` writes into a case directory whenever its
stub sees a request the case log does not cover, and removes again
once a derivation records zero misses. It can appear transiently
between a failed derivation and the `harness capture --case <dir>`
that resolves it (see "The miss-file mechanism" below); a case
directory carrying one mid-review means a capture is owed, not that
the fixture itself is broken.

`case.json` decodes into `cassette.Case`. Its `requests` field is the
committed request log: an expectation the harness replays against, not
scaffolding to regenerate. A response body lives only as a file under
`responses/`; `case.json` never embeds one inline, so there is never a
decode-and-re-encode step that could disturb its bytes. `Case.Extra`
lists response files a case captured but no logged request currently
consumes: recall-extension fixtures for a future candidate-widening
improvement (U8), graded on the same shared subset rather than escaping
the harness.

## The structural stratum

Pass 2b's own cases: 61 of them across 15 shape families
(`docs/superpowers/research/2026-09-02-beets-structural-stratum-inventory.md`,
section (b)), each a synthetic release built through `harness synth`
rather than a live capture: matcher-behavior coverage, where the smoke
corpus above is machinery coverage. Together with the smoke corpus's
seven live cases, the structural and smoke strata commit 68 cases;
pass 2c's real-catalog stratum (below) adds to that total batch by
batch, so `ls corpus/cases | wc -l` is always the count to read off
the tree directly (no case counts itself twice: every id under
`corpus/cases/` appears exactly once as a case row, in one
family table below, the smoke table above, the real-catalog
stratum's own table further down, or the adversarial stratum's
three case tables after it, `adv-ft-*`, `adv-remix-*`, and
`adv-assign-*`; the alias subsection's table is a cross-reference
into the real-catalog stratum's own rows, not a further case
listing). Every row names the
case's family, the structural shape it exercises, and its hand-edit
column: an edit to the generated `responses/001.json` made before the
case's first freeze, reached only for a shape `ReleaseSpec` cannot
otherwise express (the response hand-edit escape hatch,
staleness-corrections ruling 3). The routine empty-search fallback
response a fallthrough case adds (a hand-written empty search result
plus a hand-added `requests` entry, "Authoring a synthetic case" step 3
below) is the sanctioned default and is never itself a named hand-edit.

### Family 3: various artists and artist handling

`va-*` plus `nonva-va-artists-misflag`, 7 cases. `test/autotag/test_distance.py`'s
`test_albumartist` (both `va` parameters), `test_comp_no_track_artists`,
and `test_comp_track_artists_do_not_match`, plus `distance.py`'s
`VA_ARTISTS` tuple (l.29), exercising `distance()`'s va-conditional
album-level `artist` skip (distance.py:447) and `track_distance`'s
`incl_artist` gate (distance.py:404-410) directly, and (the family's
seventh shape) `match.py:453`'s separate `va_likely` heuristic inside
`tag_album`. The inventory's own shape list under-counts by one
against its own budget column: it names six shapes (VA exact, VA
mismatched track artist, VA absent per-track credits both sides,
non-VA correct artist, non-VA wrong artist, a non-VA release whose
artist string collides with `VA_ARTISTS`) but budgets seven cases.
`va-track-mismatch-one` and `va-track-mismatch-all` resolve the count
here: the single mismatched-track-artist shape splits into a one-track
deviation (`va-track-mismatch-one`, still `strong`) and every-track
deviation (`va-track-mismatch-all`, crossing into `medium`), the same
doubling technique family 2 uses between its `-one`/`-two` pairs,
rather than inventing a case with no distinguishing code path from one
already covered. `va-missing-track-artists` hand-edits its generated
response (staleness-corrections ruling 3): `ReleaseSpec`'s
`artist_credit` always falls back to the release-level artist rather
than emitting a genuinely empty credit, so the candidate side of
"absent on both sides" is reached only by editing
`responses/001.json`'s `recording.artist-credit[0].name` and its nested
`artist.name` to `""` after synth, before the first freeze; the item
side is expressible directly, an ordinary `field` override setting
`artist` to `""`. `va-nonva-wrong` needed both `artist` and
`albumartist` overridden, not `artist` alone:
`get_most_common_tags` (`beets/util/__init__.py:842-844`) substitutes
the item consensus `albumartist` for `artist` whenever `albumartist` has
unanimous non-empty consensus across items, so a wrong-artist case that
only touches the `artist` field is silently overridden back to a
correct match. `nonva-va-artists-misflag` needs the same double
override for the same reason, plus a real (non-`VariousArtists`) release
so that `distance()`'s own `album_info.va` gate (distance.py:447) never
fires: the shape under test is a *different* code path,
`tag_album`'s own `va_likely` guess (match.py:451-455), which is
computed from the submitted metadata rather than from the candidate. A
`VA_ARTISTS`-colliding artist string is one of `va_likely`'s three
disjuncts (`search_artist.lower() in VA_ARTISTS`) independent of
whether the release itself is various-artists; the record's own
`distance()` computation, by contrast, keys strictly off
`album_info.va` (the candidate's own MusicBrainz artist-credit id), so
a genuinely single-artist release with a colliding submitted artist
string still takes the album-level `artist` penalty
(`distance.py:447-448`) exactly like any other wrong-artist non-VA
case. That penalty is what keeps the ID-lookup candidate from
resolving `strong` on its own (`match.py:436-442`'s early return),
which is what forces `tag_album` on to the search-fallback branch
where `va_likely` is actually consulted; a case whose ID match already
lands `strong` never reaches match.py:453 at all.

## The adversarial stratum

Pass 2c's crafted cases (Tasks 16 through 18): synthetic releases built
through `harness synth`, each one designed to make a *known*
pinned-beets matching defect actually change a verdict. Two hypotheses
in this stratum depart from that shape. The alias-mis-selection
hypothesis (below) is probed against four already-committed
real-catalog cases (Task 4's `real-nonlatin-*` rows) rather than a
synthetic case of its own, since real alias arrays are the whole point
of that class and a synthetic release cannot carry MusicBrainz's own
alias data. Task 18's `#6358` locale-toggle regression check (below) is
probed through one new case, `real-nonlatin-utada-first-love-locale`,
that is itself a real capture rather than a synth-built one: the
mechanism it probes, `_preferred_alias`, needs a real release's own
documented locale alias to fire at all. Where the structural stratum
proves the matcher's code paths and the real-catalog stratum proves
conformance over real document shapes, this stratum proves that the
oracle is measurably
wrong in named places, which is what ladder entry 2's ruling 2 (tier
one is measured against release truth where the oracle is
known-defective) exists for. Every case here carries a row in
`corpus/analysis/oracle_bugs.json` under the hypothesis it probes and a
row in `corpus/analysis/adjudications.json`. Both are the owner's to
rule on, and neither is self-adjudicated. Batch 1 was ruled by the
owner on 2026-09-04: all 21 adjudication rows carry a disposition, 18
`oracle-wrong` and 3 `oracle-correct`, and none is pending.

**Reproduction is the deliverable, not the case file.** A case that
freezes cleanly but leaves the record where a defect-free oracle would
have left it has proved nothing. The string-heuristic classes below
(`adv-ft-*`, `adv-remix-*`) name two numbers per row: the distance the
committed record actually carries, and the distance the same record
would carry if the defect were fixed. The defect-free figure is
computed against pinned beets' own `string_dist` with one edit to
`SD_PATTERNS` and nothing else (a word boundary added before the
featuring trigger, or the two 0.3-weight bracket patterns removed, which
is arithmetically the same as charging a parenthetical at full weight).
The computation is checked both ways: run with `SD_PATTERNS` untouched it
reproduces every committed record's own penalty to the last digit, which
is what makes its counterfactual half worth reading. Every case in
those two classes moves its verdict from `strong`/`apply` to
`medium`/`skip`; none of the ten failed, and no construction attempt
was abandoned. The assignment-gap class (`adv-assign-*`) proves a
different shape of wrongness: the *album-level verdict never moves at
all*, landing `strong`/`apply` on every one of its six cases, while the
per-track `assignment` and `applied_fields.title` are provably wrong
against release truth known by construction—the sharpest evidence
that class produces, per the plan's own framing. The alias hypothesis
proves a third shape again: on real, captured data, two of Task 4's
`real-nonlatin-*` cases show `artist`/`albumartist` silently
overwritten with a string other than the release's own credited
display, independent of any threshold crossing; see "Alias and
transliteration mis-selection" below.

Two features of the construction are worth stating once, since every row
below shares them. First, an item set here describes a genuinely
different release from the candidate it is matched against, and release
truth is known by construction because both releases are invented for
the probe. Second, the corpus's `mb_albumid` fencing rule ("The synth
tool") makes every item carry the candidate's own release id, so
`album_id` reads 0 and the string components are the only signal the
matcher has left. That sharpens each probe rather than weakening it: the
string heuristics are exactly the surface these defects attack.

### The featuring-pattern false positive

`adv-ft-*`, 6 cases, probing `oracle_bugs.json`'s `bug-ft-pattern`
(`742ebdf69`, `7b59604c5`, `19d091440`). `SD_PATTERNS`' featuring
discount, `[\[\(]?(featuring|feat|ft)[\. :].+`, has carried no word
boundary before its trigger since 2010, so it fires on the `ft` inside
any ordinary English word that ends in those two letters and is followed
by a space, a period, or a colon: `Draft`, `Left`, `Gift`, `Soft`,
`Craft`, `Theft`. Everything from that point to the end of the string is
deleted as though it were a featuring credit, and whatever difference
lived there is charged at the pattern's 0.1 weight instead of in full.

**These are the false-positive twin of family 4's
`strdist-feat-strip`, and the difference is the whole point.** There, the
candidate album really is `Nightbound (feat. Wren Salt)` and the item tag
really is `Nightbound`: the trigger is a genuine featuring credit, the
strip is correct, and the 0.1 weight is beets deliberately treating a
dropped credit as a small divergence rather than a large one. Here the
trigger is an ordinary word in the middle of a title or a name, nothing
is a credit, and the same 0.1 weight discards up to 90 percent of a real
difference between two unrelated releases. The mechanism is identical;
only the word boundary tells the two apart, and pinned 2.13.1 does not
have one. No case in this family hand-edits a generated response: the
defective verdict is `strong`, so beets' own early return retires the
search fallback and one release document is the whole fixture.

### Per-pair track-assignment rejection gaps

`adv-assign-*`, 6 synthetic cases, probing `oracle_bugs.json`'s
`bug-assignment-rejection-gap` (`#2981`, open since 2018; `#6078`,
2025). `assign_items` (match.py:53-81) builds a full item-to-track cost
matrix from `track_distance` and hands it to `lap.lapjv`, which always
returns a complete minimum-cost mapping: it never rejects a pair,
however costly, and never leaves an item and a track both unmatched
once the counts agree. Every case here gives its item set the release's
own track count, with every item carrying the *same* title across the
whole release—the identical string against every distinct candidate
track title, so `string_dist` scores it identically regardless of which
track it is paired against, proving (not merely asserting) that title
contributes zero discriminating signal to the solve. The only remaining
signal is `track_length`, and each case tunes a pair (or more) of item
lengths to sit within `track_length_grace` (10s) of the *wrong* track
and outside it of their own true one, so `lap.lapjv`'s own optimum
picks the swap. Every case's own `claims.json` pins the wrong
`assignment` explicitly, alongside the `applied_fields.title` values a
correct mapping would never produce. **No case in this family lands
outside `strong`/`apply`**: the sharpest evidence this class produces
is that the album-level verdict never signals anything is wrong at all,
even while individual per-track titles are provably swapped. `ties.json`
records all six unique: each case's own recorded margin (the cost gap
between the solver's actual optimum and the cheapest re-solve that
forbids one of its pairs) clears the harness's `TieMargin` constant
(`internal/harness/analysis/ties.go:15`, `1e-9`) by many orders of
magnitude, ranging from 0.053 to 0.32 across the six cases -- the
wrong mapping is the solver's actual, sole optimum, not an artifact of
a near-tie the tie machinery had to disposition.

## The canonicalization rule

A case's `requests[].path_query` is the request's path plus its raw
query string, stored in canonical form: **the query's `&`-joined
`key=value` pairs are sorted byte-wise, and nothing else changes.** The
rule never decodes and re-encodes a pair. Three facts about the wire
format would not survive that round trip:

1. **`fmt=json` is forced on every request.** beets' MusicBrainz client
   always adds it; a captured request that lacks it was not actually
   issued by pinned beets.
2. **`inc=` values join with a literal `+`, but the wire form is
   `%2B`.** `inc=artists+media` is the *logical* value, one query
   parameter with a `+`-joined list, not two parameters; a decode step
   that treats `+` as a space (the `application/
   x-www-form-urlencoded` convention) corrupts it. On the wire, though,
   beets' MusicBrainz client builds its query through Python's
   `requests`, whose param encoder percent-escapes every literal `+`
   in a value to `%2B` (Task 5's live smoke corpus discovered this the
   hard way: `harness capture`'s own canonical-query builder emitted a
   literal `+` and every derivation missed on its own primary release
   lookup until the tool was fixed to encode with `url.QueryEscape`,
   matching `requests`'s escaping exactly). A captured `path_query`
   must store `%2B`, never a literal `+`, or it will never match what
   pinned beets actually requests during replay.
3. **Search queries carry Lucene escapes.** beets' search fallback
   builds a Lucene query string with its own escaping (`\"`, `\+`, and
   so on) before URL-encoding it; decoding and re-encoding can silently
   change which characters are escaped.

`cassette.LoadCase` rejects a case whose stored `path_query` is not
already in this canonical form, so a case can never depend on a replay
lookup silently reordering pairs for it. The path portion, including
any trailing slash, is never touched by canonicalization: two requests
differing only by a trailing slash name different resources and stay
distinct, they do not collapse into the same canonical key.

## The manifest

`corpus/manifest.json` pins every version the corpus's derived
`Expected` records depend on: the beets version, its
`unidecode`/`jellyfish`/`lap`/`numpy`/`mediafile` dependency versions,
the shim's own version, and a content hash per config profile.
`cassette.LoadManifest` parses the file and checks its shape only (a
schema version and a beets pin must be present); reconciling the
dependency and profile pins against a live venv is derivation-time
work, done by the oracle package's `Reconcile`.

A profile edit, or a beets/dependency version bump, is a
corpus-revalidation event exactly like any other pin change: whatever
in the manifest disagrees with the new venv is what `Reconcile` names.

`schema_version` moved from `1` to `2` in rung 2, pass 2b's Task 1:
`cassette.Expected` gained plain `weights` and `thresholds` fields
echoing the shim's `match.distance_weights` table and its
recommendation-boundary config, closing a gap where
`oracle.Derive`'s `json.Unmarshal` silently dropped both. The bump
forced a re-derivation of every committed record through the new
`harness freeze` verb (below); `internal/harness/corpus_test.go`'s
`wantManifestSchemaVersion` moved with it.

`schema_version` moved from `2` to `3` in rung 2, pass 2d's Task 1:
`cassette.Manifest` gained a `MediaFile` field pinning
`mediafile==0.17.0`, the write/read-back layer the file-tags ledger
(below) depends on, and `Reconcile`'s `pinned` tuple and
`versionProbe` string both gained their sixth component alongside it.
**This bump forced no re-freeze.** `Manifest` is corpus metadata, not
a `cassette.Expected` field, so no committed case's `case.json`
content changed; the evidence is `make derive` re-deriving all 215
committed records byte-identically with the new pin in place. This is
the one place pass 2d's schema event differs from 2b's: a schema bump
forces a re-freeze only when it moves what `Expected` itself carries,
never when it only adds a manifest pin nothing in `Expected` echoes.

## The file-tags fixture

`internal/harness/oracle/testdata/template.flac` is a vendored,
42-byte, valid, silent FLAC container carrying no tags: the four-byte
`fLaC` signature followed by one last-block STREAMINFO metadata block
(mono, 44.1kHz, 16-bit, zero samples), the minimum `mediafile`'s
reader needs to dispatch a file as FLAC. It was authored once by
`internal/harness/oracle/testdata/gen_template_flac.py`, run as
`python3 internal/harness/oracle/testdata/gen_template_flac.py` from
the pinned venv; that script is committed alongside the blob as its
provenance record and is never invoked by `make derive` or the gate.
The pure-`mutagen` route needs no `ffmpeg` or `flac` binary at all:
mutagen only needs the metadata container to be well-formed, and
mutagen is already a pinned transitive dependency of `mediafile`
(`tools/venv/requirements.txt`, "via mediafile").

`internal/harness/oracle/derive_file_tags.py` writes each subject's
item into its own fresh copy of this template and reads the result
back through an independent `mediafile.MediaFile` parse, per
`cassette.Expected.AppliedFields`' in-memory record fed forward into a
real file. The value keys this write/read-back round trip can ever
report split into two disjoint sets, both computed off the pinned venv
rather than hardcoded, and both recorded in the file-tags ledger's own
header (`corpus/analysis/file_tags.json`, see "The analyses" below):

- **The writable set, 69 keys**: `Item._media_fields` intersected with
  `MediaFile.sorted_fields()`, the fields `MediaFile.update()` actually
  iterates and therefore the only fields `Item.write()` can ever touch.
  This is the per-row value dict every subject's ledger row carries.
- **The read-only remainder, 9 keys**: `bitdepth`, `bitrate`,
  `bitrate_mode`, `channels`, `encoder_info`, `encoder_settings`,
  `format`, `length`, `samplerate`. These are audio properties
  `MediaFile` reports from a container's own STREAMINFO, never written
  by `Item.write()`; measured concretely, `length` reads back `0.0`
  regardless of what a subject's own `AppliedFields.length` says. They
  are recorded once, in the ledger's shared `template` block, since
  their values are a property of the template blob and never of any
  subject.

## The analyses

`corpus/analysis/` holds what the corpus knows about itself. Three of
its files are checked by the repository gate on every run
(`internal/harness/analysis`, pure Go over committed files, no venv and
no network); two of those three are also re-derived under `make derive`,
because measuring them needs beets.

### `claims.json`, one per case

Every committed case carries a sibling `claims.json` naming what its
author read off the derived record: `best_album_id` and
`recommendation` always, `min_candidates` (default 1), the family's
`penalty_keys_nonzero`, `penalty_keys_zero`, and `penalty_keys_absent`
against the best candidate's own penalties, and, where the family
calls for it, `assignment`, `extra_items_len`, `extra_tracks_len`, and
`applied_fields` spot values. It deliberately sits outside
`cassette.Expected`: the record schema is frozen, and a claim is a
reading of a record rather than part of one.

The claims are what keep a degraded case from freezing green. A case
whose candidate list collapsed, whose best release changed, or whose
family penalty stopped firing still re-derives to a self-consistent
record; only a claim written against the behavior the case exists for
notices. The gate fails on any mismatch, on a case with no
`claims.json`, and on a claim key no parser recognizes. A claim key
claimed zero must be present in the record at 0.0 rather than absent,
since beets adds a key at 0.0 and still counts it in the normalizer's
denominator. A key claimed absent is the counterpart: it must not
appear in the best candidate's penalty map at all, distinguishing a
key beets never added from one added and zeroed.

**`min_candidates: 0` declares the zero-candidate mode**, the shape a
case whose only candidate release was dropped by beets' own
`_add_candidate` (a zero-track release) needs: `best_album_id` is left
out entirely (there is no best candidate to name one from), and the
checker asserts the record's candidate list is actually empty rather
than treating zero as a trivially-satisfied lower bound, so the mode
can never mask a case whose candidate list is merely degraded rather
than genuinely empty.

### `proximity.json`, the threshold-proximity flag

The flag is pure Go and needs nothing but the committed record. It
computes the best distance `d`, and the gap to the second candidate
where there is one, and flags a case when `d` sits within 1e-6 of the
record's own `strong_rec_thresh` or `medium_rec_thresh`, or the gap
within 1e-6 of `rec_gap_thresh`. The thresholds come from the record's
echo, never from a constant: a case derived under a profile that moves a
boundary is measured against the boundary it actually scored under. A
record carrying no candidate at all (a zero-track candidate release is
dropped by beets' `_add_candidate`) is a named skip, never an index into
an empty list.

The epsilon is the mechanics study's: beets compares the strong
threshold with a strict `<` and the medium one with `<=`, and no float
tolerance papers over a comparison-direction disagreement.

**A flag is not a failure; an unacknowledged flag is.** The gate
recomputes every case's flag and diffs it against this ledger, failing
on a case flagged but unlisted, a listed case no longer flagged, listed
boundaries that have moved, and a listed case with no written reason. No
case in the smoke corpus is flagged today, so the ledger is empty and
the flag's own proof that it fires lives in
`internal/harness/analysis/testdata/records/`: hand-authored records
parked exactly on a boundary, which are never corpus cases.

### `ties.json`, the assignment-tie detector

`lap.lapjv` picks one optimal assignment. When several assignments share
the minimal cost, a Go solver may pick a different one, so ladder entry
2 requires every tied case to be excluded or pinned. The detector splits
across the build-tag boundary because its raw material does: measuring
uniqueness needs the full item-by-track cost matrix at
`incl_artist=False`, which only beets can compute.

`internal/harness/oracle/derive_ties.py` starts the same replay stub and
rendered profile a derivation runs under, fetches the best candidate's
tracks through the plugin's own `album_for_id` (`Candidates[0].AlbumID`
is the selector for every case), and builds `assign_items`' matrix
exactly as beets does, `lap.lapjv`'s `extend_cost` padding included. It
then solves for the optimal cost `z`, and for each assigned pair
re-solves with that pair forbidden, giving `z_ij`. The optimum is unique
exactly when `min z_ij > z + 1e-9`. All three numbers are recorded, not
only the verdict, so a case that becomes tied later shows up as a moved
number rather than a silent flip.

The gate checks coverage and adjudication: every corpus case has a row,
every tied row carries a disposition (`excluded` or `pinned`) with a
reason, and no row claims a uniqueness its own recorded costs deny.

**A case whose record carries no candidate gets a skipped row**
(`"status": "skipped"`) instead of a measured one, mirroring
`proximity.json`'s own skip: there is no candidate to ask the tie
question about, so `DeriveTies` never starts the replay stub for it. A
skipped row carries a `reason` and no `album_id` or `disposition`; its
cost fields serialize as zeros and are ignored when status is
`"skipped"`. A case with no row at all is still a missing-coverage
failure, skipped or not.

Two live smoke cases are genuinely tied. `should-ask` and
`should-reject` both corrupt several items into interchangeable garbage,
and permuting those items among their tracks costs exactly the same;
both are pinned, with the reasoning in their rows.

### `components.json`, the component derivation table

`internal/harness/oracle/derive_component.py` is the second, narrower
beets entry point: no stub, no `tag_album`, no MusicBrainz response, and
no rendered profile, because a call to a distance primitive touches none
of them. It reads literal argument tuples mirroring
`test/autotag/test_distance.py`'s parametrize tables, calls the real
`Distance.add_*` method, `string_dist`, or `track_distance` per row, and
emits row id, method, arguments, and observed output. Coverage spans
every adder, the raw/max/normalized arithmetic including the
zero-weight denominator rule and the key added at 0.0, the
`generic_penalty_keys` exclusion, `string_dist`'s full pipeline, the
`SD_PATTERNS` relative-weight rows, and the whole
`TestDataSourceDistance` parameter space, which the tool reaches
in-process by overriding `distance_weights` and swapping
`find_metadata_source_plugins` exactly as beets' own test does. It runs
under beets' shipped defaults, which is where both corpus profiles leave
the `match:` surface anyway.

**Be clear about what the gate asserts over it.** The Go matcher those
outputs will be compared against does not exist until rung 3. The
gate-resident test checks schema validity, row-id uniqueness,
non-emptiness, a per-method coverage set, and a row-count floor, and
nothing more. It is not a conformance check. The re-derive-and-diff
assertion is oracle-tagged and runs under `make derive`.

### Regenerating a derived ledger

`ties.json`, `components.json`, `file_tags.json`, and `album_info.json`
are derived, so they are rewritten rather than hand-edited:

```sh
go test -tags oracle ./internal/harness/oracle -run Ledger -update-ledgers
go test -tags oracle ./internal/harness/oracle -run Component -update-ledgers
go test -tags oracle ./internal/harness/oracle -run FileTags -update-ledgers
go test -tags oracle ./internal/harness/oracle -run AlbumInfo -update-ledgers
```

A regeneration is expected to be a no-op unless the venv's pins moved
(a `mediafile` or `beets` bump for `file_tags.json`); the re-derive
test diffs the fresh run against the committed file and fails loudly
with a pointer back to this command whenever the two disagree. An
update carries every tie row's `disposition` and `reason` forward:
those are human adjudication, and a re-measurement has nothing to say
about them. `proximity.json` has no derived half at all, so its rows are
written by hand; the gate names exactly which ones are owed.

### The adjudication artifacts

`adjudications.json` and `oracle_bugs.json` are pure Go and hand-written,
never derived: neither needs the venv or a `make derive` run, and both
are checked on every `bash scripts/check.sh` by
`internal/harness/analysis`.

**`adjudications.json` is the general divergence row**, designed
forward-compatible with rung 4 (Shadow): the build spec names a
divergence log and an adjudication artifact there for a structurally
identical problem, a human ruling on a matcher disagreement from a
written artifact alone. This pass originates the schema. A row's
`subject` is the join key back to the oracle's own record rather than a
re-transcription of it (`cassette.Expected` already holds
recommendation, action, distance, and the best candidate's full penalty
breakdown): either a corpus `case_id`, or an `album` plus
`release_mbid` pair for a live shadow divergence, never both and never
neither. A row also carries `suspected` (what is suspected wrong and
why, in prose, with its `citation`, an issue number or an
evolution-lessons finding id such as `U1/ft-pattern`), `release_truth`
(the correct verdict with its own citation, or an explicit statement
that the input material has no correct MusicBrainz entry at all), and
`disposition` plus `reason`, the same two-field shape `ties.json`
already uses, plus `adjudicator` and `date`.

**`oracle_bugs.json` is one row per known-defect hypothesis, not one
per case.** A hypothesis may be probed by several cases, or by none. A
row carries `bug_class` and `citation`, `probe_case_ids`, a
`reproduced` field (`yes`, `no`, or `not-attempted` with a
`reproduced_reason`, agent-settable, since it is a machine-observable
fact about whether a probe case moved the verdict), `adjudication_refs`
pointing at the `adjudications.json` rows the probes produced, and the
same `disposition`/`reason`/`adjudicator`/`date` fields as
`adjudications.json`. A hypothesis that does not reproduce is still a
written row, matching the corpus's standing "an unacknowledged flag is
a failure" discipline: a checked-and-cleared hypothesis is never
silently dropped.

**`pending-adjudication` is a legal disposition here and an illegal one
at the launch gate.** The gate accepts a `pending-adjudication` row with
a written suspicion and written release truth; it fails a row with a
missing disposition or one no parser recognizes. Recognized
dispositions: `pending-adjudication`, `oracle-wrong` (carrying the
adjudicated correct verdict in `corrected_verdict`), `oracle-correct`
(the crafted case failed to reproduce the suspected defect), and
`no-correct-answer` (the material has no correct MB entry). It is the
**launch gate**, a different gate at a different time, that refuses an
unadjudicated row; this pass's own gate accepts one sitting at
`pending-adjudication` indefinitely.

**`disposition` is owner-only** (never self-adjudicated). `reproduced`
is a field an agent may set; `disposition` is never set by an agent to
anything but `pending-adjudication`, including a row whose written
evidence looks unambiguous. An agent-authored row carries the reserved
sentinel `"agent"` as its `adjudicator`; only a row whose `adjudicator`
is something else (a human name) may carry a disposition other than
`pending-adjudication`. The gate-resident checker enforces this and
ships a fixture proving it fires: an `adjudicator: "agent"` row cannot
be committed carrying `oracle-wrong` or any other ruled disposition.

## Handoff to rung 8: what pure-Go FLAC tag writing may assume

Ladder entry 8 names its own precondition: pure-Go FLAC tag writing
"proven against the corpus's expected applied tag sets from rung 2."
This section states, in writing, exactly what rung 8's implementer may
now assume from pass 2d and no more.

**The corpus carries expected applied tags at two altitudes, and they
are not interchangeable.**

1. **`Expected.AppliedFields`, on every one of the 215 committed
   cases**, is the in-memory record `match.apply_metadata()` produces:
   what beets decided to set on an `Item`, before any write. This is
   not a conformance target for a file-tag writer. It carries fields
   `Item.write()` never touches at all (bookkeeping and read-derived
   values outside `Item._media_fields`), and it says nothing about what
   actually lands in a container, because it was never written to one.
2. **`corpus/analysis/file_tags.json`, on the twelve subjects named
   in "The whole-corpus case inventory" above and detailed in
   "`file_tags.json`, the file-level applied-tag ledger" below**, is
   what pinned beets' own write path actually put into a real FLAC
   container and what an independent `mediafile.MediaFile(path)` read
   back afterward. This is the conformance target.

**The writable-set rows are the conformance target; the read-only
`template` block is never one.** Every subject row in `file_tags.json`
carries values only for the 69-key writable set (the ledger's own
`writable_fields` header, reproduced here so rung 8 has it without a
second lookup): `acoustid_fingerprint`, `acoustid_id`, `album`,
`albumartist`, `albumartist_credit`, `albumartist_sort`,
`albumartists`, `albumartists_credit`, `albumartists_sort`,
`albumdisambig`, `albumstatus`, `albumtype`, `albumtypes`,
`arrangers`, `artist`, `artist_credit`, `artist_sort`, `artists`,
`artists_credit`, `artists_sort`, `asin`, `barcode`, `bpm`,
`catalognum`, `comments`, `comp`, `composer_sort`, `composers`,
`country`, `day`, `disc`, `disctitle`, `disctotal`, `encoder`,
`genres`, `grouping`, `initial_key`, `isrc`, `label`, `language`,
`lyricists`, `lyrics`, `mb_albumartistid`, `mb_albumartistids`,
`mb_albumid`, `mb_artistid`, `mb_artistids`, `mb_releasegroupid`,
`mb_releasetrackid`, `mb_trackid`, `mb_workid`, `media`, `month`,
`original_day`, `original_month`, `original_year`,
`r128_album_gain`, `r128_track_gain`, `remixers`, `rg_album_gain`,
`rg_album_peak`, `rg_track_gain`, `rg_track_peak`, `script`,
`subtitle`, `title`, `track`, `tracktotal`, `year`. A pure-Go writer
proves conformance by writing these fields and reading them back the
same way `derive_file_tags.py` did.

The nine-key read-only remainder — `bitdepth`, `bitrate`,
`bitrate_mode`, `channels`, `encoder_info`, `encoder_settings`,
`format`, `length`, `samplerate` — sits once in the ledger's shared
`template` block, never in a subject row, and is never a per-subject
target for any writer: these are audio properties a reader gets from
the container's own `STREAMINFO`, not from anything `Item.write()`
ever sets. Concretely, `length` reads back `0.0` on the vendored
template blob regardless of a subject's own `AppliedFields.length`; a
rung 8 conformance test that expects a writer to reproduce a read-only
key against a case's own value is testing a fact the corpus never
established.

**The pin and its failure mode.** `mediafile==0.17.0` is pinned in
`corpus/manifest.json` (`schema_version` `3`), and `Reconcile`'s
`pinned` tuple and `versionProbe` string both name it: a `mediafile`
bump the corpus has not re-derived against fails `make derive` loudly
rather than silently drifting.

**Where the fixture lives.** The vendored template FLAC is
`internal/harness/oracle/testdata/template.flac` (42 bytes, silent,
untagged), authored once by the committed
`internal/harness/oracle/testdata/gen_template_flac.py` (see "The
file-tags fixture" above for its provenance and the pure-`mutagen`
authoring route). `derive_file_tags.py` and its Go driver,
`internal/harness/oracle/file_tags.go`, are the derivation; the
generated ledger is `corpus/analysis/file_tags.json`, regenerated per
"Regenerating a derived ledger" above and never hand-edited.

**Non-scope, stated as plainly as the scope above.** 2d ships the
evidence, not the mapping study. The close read of beets' own
apply-metadata field mapping against the `mediafile` tag layer — which
writable-set key maps to which FLAC Vorbis comment or block, and how a
pure-Go writer should represent each — is rung 8's own plan-opening
work, per ladder entry 8. So is the wazero-taglib spike. Nothing in
2d evaluates, prototypes, or rules out either.

## The capture tool

`cmd/harness` (`harness capture`) is the workstation dev tool that
populates a case's `responses/` directory from the live MusicBrainz
API. It is never shipped, and the repository gate never runs it
against the network: `go test` exercises only its request planning
and file I/O, against a fake fetcher.

Two verbs, matching the capture-derive loop's two halves:

- **`harness capture --mbid <release> --out corpus/staging/<id>`** seeds
  a case: it fetches the release lookup at beets' own maximal `inc=`
  (`RELEASE_INCLUDES`, mechanics study Q5) rather than the minimal set
  today's matcher happens to read, so a future matcher improvement
  that wants another field never forces a re-capture (U6). When the
  fetched release carries `status: "Pseudo-Release"` and a backward
  `transl-tracklisting` relation, it follows that relation and fetches
  the linked actual release too, at the same maximal `inc=` (Q5, item
  7): beets merges the two AlbumInfos internally, so a capture missing
  the second release would replay a 404 the moment pinned beets
  follows it. Both response bodies are written verbatim with
  `os.WriteFile`, never re-encoded. The seeded case carries only its
  request log; `Input`, `Profile`, and `EvalDate` are a human's job
  once a case is seeded, since none of them is derivable from an MBID
  alone.
- **`harness capture --case <dir>`** consumes an existing case's miss
  list: it fetches exactly the requests named in `<dir>/misses.json`
  (see "The miss-file mechanism" below), appends each as a logged
  `Request`, and removes the miss file once every fetch succeeds. A
  fetch failure leaves both the case and the miss file untouched, so a
  retry never loses partial progress.

**Wire discipline**, both verbs: at most one request per second within
a single invocation (the first request pays no wait; every request
after it does); every request carries the identified User-Agent
`dubplate-harness/<version> ( $DUBPLATE_HARNESS_CONTACT )`; the tool
refuses to run at all when `DUBPLATE_HARNESS_CONTACT` is unset or
empty, since MusicBrainz's terms require a reachable contact in every
request and this tool never substitutes a literal for it (CLAUDE.md's
universality rule).

### The miss-file mechanism

`internal/harness/oracle.Derive` starts a `stub.Server` over a case's
existing responses and runs pinned beets against it. When beets issues
a request the case log does not cover, the stub answers 404 and
records a `stub.Miss` (method plus canonical path+query). After the
shim process exits, `Derive` writes every miss it collected to
`<case dir>/misses.json` as a JSON array of `stub.Miss` values
(`{"method": "...", "path_query": "..."}`); when a derivation sees no
misses at all, `Derive` removes any stale file instead, so a case
directory's `misses.json` always reflects only its most recent
derivation. `harness capture --case <dir>` reads that same file and
`stub.Miss` shape directly (no separate schema to keep in sync), which
is what makes the file the load-bearing handoff between a derivation
and the next capture, rather than scaffolding a human has to
transcribe by hand.

## The seed-items tool

`harness seed-items --case <dir> [--overrides <file>]` closes the gap
`harness capture` leaves open: a seeded case carries only its request
log (per-track title, length, recording id, and the release-level
album, albumartist, and date all live in the captured response, none
of them inventable from an MBID alone), and a captured response body
is evidence, never read into agent context. `seed-items` is the
**sanctioned reader**: it opens the case's primary response
(`Requests[0].Response`), projects a correct baseline `Input.Items`
from it, and writes the result back to `case.json` through
`cassette.Case.Write`. No other code path in the corpus tooling, and
no agent directly, opens `responses/*.json`; inspect a captured case
through its derived record, its `claims.json`, and `seed-items`' own
projection instead.

**The projection mirrors `harness synth`'s own derive-then-perturb
model** (`internal/harness/synth.ProjectItems`), sourced from a parsed
captured document instead of a `ReleaseSpec`: one item per track,
release order, carrying `title` (the track's own title, falling back
to its recording's when the API leaves the track-level field empty,
matching beets' own `get_tracks_from_medium`), `length` (milliseconds
divided by 1000, the same precision the release document itself
carries), `track` (per-medium position), `mb_trackid` (the recording
id), and the release-level `album`, `albumartist`, `artist`, `year`,
and `mb_albumid`. A multi-medium release gets a `disc` field per item;
a release whose artist-credit carries MusicBrainz's well-known Various
Artists id gets `comp: true` and each item's `artist` from its own
track-level (or recording) credit rather than the release's. An
artist-credit spanning more than one entry (`"Marvin Gaye" + " & " +
"Tammi Terrell"`) is reassembled from its `name`/`joinphrase` pairs,
the same display string beets itself builds.

**`--overrides` reuses `harness synth`'s exact vocabulary**: a JSON
file of `field` / `missing` / `extra` entries, applied to the projected
baseline through the same `applyOverrides` function a synthetic spec's
perturbation step calls. A case whose axis is real MB noise or
mistagged material reaches for this the same way a structural-stratum
case reaches for a spec's own `overrides` list: the baseline is
correct by construction, and the axis's whole point is one deliberate
divergence from it.

`seed-items` never sets `profile` or `eval_date`; those are still a
human's job once a case is seeded (`harness capture`'s own doc
comment), which is also why `--case` must already resolve through
`cassette.LoadCase`: a directory missing either field fails to load
before `seed-items` ever gets to project anything into it.

**`--facts` is the sanctioned confirmation channel for a fact-verified
axis.** `harness seed-items --case <dir> --facts` reads the case's own
primary captured response, exactly as the item-projection mode does,
but never calls `cassette.Case.Write`: it prints the document's own
structural facts to stdout, deterministically formatted, and touches
nothing on disk. The fact-verified axes (reissue/remaster, multi-disc/
box-set, non-Latin, two-release) confirm a candidate release through
this mode rather than by opening `responses/*.json` directly, per the
"one sanctioned door" rule: seed the candidate via `harness capture
--mbid <mbid> --out corpus/staging/<tentative-id>`, then run
`--facts` against it to read the release date, the release-group's
own first-release-date (a year-penalty reissue's divergence point),
the release status, each disc's track count, and the release's
documented aliases (its own top-level `aliases` array plus each
artist-credit entry's own artist aliases, each with its type and
locale when the document carries them). A document that documents no
alias at all prints an explicit `aliases: none` line rather than
omitting the section, so a genuinely alias-free release is never
indistinguishable from a broken read. `--facts` may run against a case
whose `Input.Items` are already projected (it reads the same response
`seed-items`' item-projection mode does, never `Input.Items` itself),
and it rejects `--overrides` outright, since overrides only ever
perturb a projected item baseline and have no facts-mode meaning.

### Authoring a captured case

1. **Seed:** `harness capture --mbid <release> --out
   corpus/staging/<id>`. The seeded case carries only its request log.
2. **Set `profile` and `eval_date`** directly in `case.json`: both are
   trivial known values (the profile the case derives under; the
   case's own capture date, matching the smoke corpus's own
   convention), needing no tooling.
3. **Author the input:** `harness seed-items --case
   corpus/staging/<id>`, adding `--overrides <file>` for a case whose
   axis is real MB noise or a partial rip.
4. **Derive, read misses, capture, re-derive, until zero misses.**
   `harness freeze --case corpus/staging/<id>` derives and freezes.
   When beets falls through to its text search, `Derive` writes
   `misses.json` and `harness capture --case corpus/staging/<id>`
   fetches exactly what it names; each round may change the candidate
   pool, so a fallback case's item set sometimes needs a second
   `seed-items` pass (with a wider `--overrides` list) to converge.
5. **Promote, then write the owed ledger rows.** Move the frozen case
   into `corpus/cases/<id>/` first, then run `go test -tags oracle
   ./internal/harness/oracle -run Ledger -update-ledgers` so `ties.json`
   picks up its generated row, then write `claims.json` and any owed
   `proximity.json` exception row, then run both gates and commit.

## The synth tool

`harness synth --spec <file> --out corpus/staging/<id>` is the
structural stratum's own seeding tool (rung 2, pass 2b): where
`harness capture` seeds a case from a live MusicBrainz release,
`harness synth` seeds one from a compact, hand-written release spec,
since every structural case invents its own release rather than
capturing a real one. It emits `case.json` (the input items, in pinned
order; the profile; the eval date; and the ID-lookup request log, in
canonical form) plus `responses/001.json` (the WS/2 release document
that request log names), and never touches the network.

A spec names one release: `album`, `artist`, `date`, `country`, an
invented `mb_albumid`, the `profile` and `eval_date` the case derives
under, and a `media` list of per-medium track lists (`title`, `length`,
`position`). A handful of flags cover the families that need them:
`various_artists` (sets MusicBrainz's own well-known Various Artists
artist id on the release credit, the sole signal beets' musicbrainz
plugin reads to set `AlbumInfo.va`), a per-track `artist_credit`
override, `label` / `catalog_number`, and `disambiguation`.

**`original_date` moves the release-group's own first-release-date away
from `date`**, the field a year-penalty reissue case (family 7) needs:
absent, the release-group's first-release-date equals `date` (today's
behavior, no divergence between a release and its group's original
date); a non-empty value names the group's own earlier or later
original date directly; an explicit empty string emits an empty
release-group first-release-date, the "no original date on record"
shape beets reads as absent. Every derived item's own `year` tag
still comes from `date` alone (`original_date` never touches item
generation), so a case that wants the items themselves to diverge
from both dates still reaches for an `overrides` entry on `year`.

**Items are derived from the release by default, then perturbed.** The
common shape across almost every family is "a correct item set with
one deliberate divergence," so a spec expresses its item set as the
release's own tracks (one item per track, release order) plus an
`overrides` list of small, explicit perturbations, rather than
restating every field for every item. Each override names an `op`:

- `field` merges `fields` onto the derived item at `index` (a wrong
  title, a wrong year, a wrong `data_source`, ...).
- `missing` drops the item at `index` entirely, leaving its candidate
  track unmatched (`extra_tracks`).
- `extra` appends a brand-new item carrying `fields`, unmatched to any
  candidate track (`extra_items`).

**`mb_albumid` is fenced off the override list outside family 10.**
beets picks the release it looks up from `current_metadata`'s
most-common `mb_albumid` value across items; perturbing it on enough
items changes which release gets fetched, which is unanswerable under
the no-failing-request constraint below, since a case cannot depend on
a request that fails. `harness synth` rejects a `field` or `extra`
override that sets `mb_albumid` unless the spec sets
`allow_album_id_override` (family 10 only), and an `extra` override
always carries the release's own `mb_albumid`, like every other item,
regardless of what its own `fields` name. A family that needs a wholly
independent item set, unrelated to the release's own tracks, can
supply one via the spec's `items` field directly; `overrides` is
ignored in that mode.

**Canonical form is produced, never hand-typed.** The request log's
`path_query` goes through the same query-canonicalization rule this
file documents above (including the `%2B`-escaped `inc=` join), so a
generated case never depends on a literal a human happened to type
correctly.

### Authoring a synthetic case

1. **Write a spec** naming the release and its perturbation from a
   correct baseline (a wrong title, a missing item, an extra item,
   ...), and run `harness synth --spec <file> --out
   corpus/staging/<id>`. The case directory it writes is gitignored:
   nothing under `corpus/staging/` is ever a committed fixture.
2. **Freeze and read the misses.** `harness freeze --case
   corpus/staging/<id>` derives the case. A structural case is
   deliberately imperfect (most of the corpus's families), so pinned
   beets falls through to its text-search fallback exactly as the live
   `should-ask` and `should-reject` cases did; that request arrives as
   a miss, not a failure, and freeze writes `corpus/staging/<id>/
   misses.json` naming it.
3. **Hand-author a response for every miss**, most often the search
   fallback. The default answer is an empty search result: a
   well-formed WS/2 search document with zero releases (`created`,
   `count: 0`, `offset: 0`, an empty `releases` array), the same shape
   `corpus/cases/should-ask/responses/002.json` carries with its
   `releases` array emptied, saved as the case's next response file
   and referenced by a hand-added `requests` entry at the miss's own
   `path_query`. An empty search result keeps the candidate set to the
   single looked-up release, which is what a structural distance case
   wants; family 10 is the pass's only shape whose search response
   deliberately returns a release (see the plan's Task 10).
4. **Re-derive, iterate to zero misses, then promote.** Re-run
   `harness freeze --case corpus/staging/<id>` until it records no
   misses at all; freeze refuses to write a record while any remain,
   so a case directory with no `misses.json` and a non-nil `expected`
   is the loop's own fixed point. Promotion to `corpus/cases/<id>/` is
   a plain move once the case's `claims.json` and both analysis-ledger
   rows are written (Task 3's checks).

## The freeze tool

`harness freeze --case <dir>` is the capture-derive loop's other half:
it derives the case at `<dir>` and writes the returned record back
through `cassette.Case.Write`, the repeatable path a case moves from
`corpus/staging/<id>/` (or an already-committed `corpus/cases/<id>/`)
to a frozen record. It is the only place in this repository that
writes a case's `expected` field; every committed record, including
the seven-case smoke corpus, is written by it and never hand-edited.

`--case` is authoritative for any directory: `oracle.Derive`'s
`Options.Dir`, when set, overrides its own `corpus/cases/<ID>`
default, so freeze works the same way against a staging case that has
never been committed and against an already-frozen one being
re-derived after a schema or profile change. Freeze refuses to write
when the derivation leaves `misses.json` behind: an unanswered
request means the case is only half-derived, and freezing it would
commit a record its own request log cannot reproduce. Freezing an
already-normalized case twice in a row changes nothing but its
`expected` field: `cassette.Case.Write` re-marshals `Input`
deterministically, so the second freeze's `id`, `input`, `profile`,
`eval_date`, `requests`, and `extra` bytes match the first's exactly.

Freeze derives against the pinned uv venv at `tools/venv/.venv`
(tools/venv/README.md) by default. Set `DUBPLATE_ORACLE_VENV` to point
it at a venv built somewhere else; `internal/harness/oracle`'s own
oracle-tagged tests, `make derive`'s whole run, and every case-
authoring task's freeze invocations all honor the same variable, so a
venv built once outside the repository root works everywhere freezing
happens.

### A recorded fixed point, not a stable request set

The capture-derive loop (capture, derive, capture the derivation's
misses, derive again) converges when a derivation records zero misses.
That convergence is a **fixed point of one specific pinned-beets run
against today's captured data**, not a promise that the request set
itself is stable or minimal. In particular, a strong ID-lookup match
retires beets' search fallback for that item: once a release lookup by
MBID scores a strong recommendation, beets never issues the search
request an earlier, less complete capture might have needed. Any
response already captured for that now-unreachable search request does
not become wrong; it becomes `Extra` (recall-extension surface, U8),
legally orphaned by a more complete capture rather than a regression
to fix. A case's `Extra` list is exactly where those orphaned
responses belong once a maintainer notices the loop has converged past
needing them.
